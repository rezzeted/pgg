# Техническое задание: язык и движок процедурной генерации геометрии (PGG)

**Статус:** черновик v0.5 · **Назначение:** самодостаточная спецификация для агента-разработчика, реализующего систему с нуля. История правок — в разделе «Изменения» (§19).

---

## 1. Цель и мотивация

### 1.1. Что строим

Систему процедурной генерации геометрии для игрового движка, состоящую из двух компонентов:

1. **Текстовый язык описания графов генерации** (рабочее название — PGG, Procedural Geometry Graph). Текст — источник истины: файлы `.pgg` хранятся в репозитории, диффаются, ревьюятся.
2. **Движок исполнения (runtime)**: парсинг, валидация, ленивое вычисление графа, кэширование, отладочные пробники, экспорт геометрии в форматы движка.

Поверх языка впоследствии строится **нодовая проекция** — визуальное представление графа для человека (просмотр, навигация, отладка). Проекция — производная от текста, а не отдельный формат хранения.

### 1.2. Зачем это нужно

Генерация окружения (камни, скалы, террейн, разброс объектов) ручным моделированием не масштабируется, а процедурные пайплайны, записанные кодом общего назначения, плохо читаются, не кэшируются по частям и не отлаживаются визуально. Отраслевые эталоны — Geometry Nodes в Blender и SOP-сети в Houdini — доказали жизнеспособность модели «граф преобразований геометрии». Настоящий проект переносит эту модель в среду игрового движка с двумя принципиальными отличиями:

- **Первичный автор кода — LLM-агент, а не человек.** Язык проектируется под машинную генерацию и самокоррекцию по сообщениям об ошибках. Человек — вторичный потребитель: читает, ревьюит, правит, отлаживает через нодовую проекцию и пробники.
- **Воспроизводимость и кэширование — требования рантайма движка**, а не редакторская фича: один и тот же граф с теми же входами и генераторами должен повторяться независимо от порядка потоков; межплатформенная битовая идентичность всей float-геометрии не требуется. Интерактивная правка параметров пересчитывает только затронутые подграфы.

### 1.3. Контекст решаемой задачи

Типовой сценарий, ради которого строится система (генерация скального образования):

1. Взять базовую форму (икосфера, SDF-примитив, облако точек).
2. Деформировать слоистым шумом (FBM-дисплейс вдоль нормалей).
3. Править топологию (SDF-булевы, сварка вершин, сглаживание).
4. Вычислить производные данные: нормали, крутизну склона, кривизну, относительную высоту.
5. Построить маски («круто», «плоско», «высоко», «мокро») и сохранить их как именованные группы на геометрии.
6. Разбросать по поверхности точки с плотностью из масок; разместить на точках инстансы (камни поменьше, обломки, мох) с per-instance вариативностью.
7. Записать атрибуты для материалов и физики (vertex color, wetness, biome).
8. Сэмплить соседнюю геометрию (поставить объект на террейн, перенести с террейна атрибуты).
9. Собрать всё в переиспользуемые супер-узлы (`make_rock`, `cliff_wall`) и скомпоновать в граф мира с воспроизводимыми генераторами чанков.

Из сценария следуют ключевые нагрузки: **десятки тысяч инстансов**, **FBM-шумы по миллионам элементов**, **повторные вычисления одних и тех же полей в разных потребителях**, **итеративные процессы** (эрозия, релаксация разброса), **агрегации** (нормировка на размер, число островов).

### 1.4. Не-цели

- Физическая симуляция в реальном времени (ткани, жидкости) — вне объёма; итеративные процессы ограничены генеративными (эрозия, рост, релаксация).
- Полноценный рендер/материалы — система отдаёт геометрию и атрибуты, шейдинг остаётся на стороне движка.
- GUI-редактор — отдельный проект поверх готового языка и runtime API.

## 2. Нефункциональные требования

| # | Требование | Критерий проверки |
|---|---|---|
| N1 | **Воспроизводимость.** В рамках одной версии runtime, backend'а и numeric profile одинаковые файл, параметры и `rng` дают одинаковый результат независимо от числа потоков. Случайные слова для одинакового `(rng, counter, lane)` бит-в-бит стабильны между платформами; вся float-геометрия — нет | хэш результата стабилен между повторными прогонами одного profile; межплатформенные тесты проверяют RNG-векторы, инварианты и численные допуски |
| N2 | **Ленивость.** Поля не вычисляются без потребителя; граф тянется от запрошенных выходов | пробник на середину графа не вычисляет узлы ниже по потоку |
| N3 | **Кэширование.** Результат подграфа переиспользуется по ключу (структура, параметры, идентичности входов и `rng`, numeric profile) | повторный прогон без правок — 100% cache hit при достаточной ёмкости кэша |
| N4 | **Инкрементальность.** Правка файла инвалидирует только подграфы ниже изменённого определения | смена параметра в конце файла не пересчитывает начало |
| N5 | **Статическая проверяемость.** Ошибки типов и контрактов атрибутов ловятся до запуска вычислений | файл с отсутствующим атрибутом отклоняется валидатором без генерации |
| N6 | **Машинная поправимость ошибок.** Каждая ошибка: код, строка, ожидание/факт, готовый паттерн исправления | LLM исправляет типовую ошибку за одну итерацию |
| N7 | **Параллелизм.** Per-element вычисления полей и foreach по кускам параллелятся без гонок | в одном numeric profile результат не меняется при 1/2/N потоках |
| N8 | **Масштаб.** 10⁵ инстансов, 10⁶ точек в поле — рабочий режим, а не предел | бенчмарк-сцена укладывается в целевое время генерации чанка |

## 3. Архитектура системы

Три слоя, физически разделённые в одном текстовом файле:

```
┌─────────────────────────────────────────────────┐
│ Слой визуала: layout-подсказки в комментариях   │  ← только для нодовой проекции
├─────────────────────────────────────────────────┤
│ Слой диагностики: инспекторы, tap, пробники     │  ← чистые, ленивые, срезаются флагом
├─────────────────────────────────────────────────┤
│ Слой семантики: SSA-поток определений, зоны,    │  ← единственное, что влияет на выход
│ def/импорты, param                              │
└─────────────────────────────────────────────────┘
```

Компоненты runtime:

1. **Парсер** → AST.
2. **Форматтер** (канонический, в стиле gofmt): любой вход приводится к единственному виду — минимальные diff'ы при машинных правках. Поскольку блоки — скобочные, форматтер способен канонизировать **любой** синтаксически корректный текст независимо от его отступов.
3. **Валидатор**: типы, вывод схемы атрибутов сквозь границы def, контракты expect/ensure, rng-дисциплина, разрешение имён и импортов.
4. **Планировщик**: топологический порядок (совпадает с порядком в тексте), dirty-propagation, разбиение на задачи.
5. **Исполнитель**: ленивые поля с memoization, материализация геометрии в checkpoint-точках, пул потоков, опциональный GPU-backend для полей.
6. **Кэш**: по ключу (хэш подграфа, параметры, идентичности входов и `rng`, numeric profile); persistent-кэш между сессиями — опционально.
7. **Пробник-сервис**: исполнение инспекторов по адресу (ребро, экземпляр), форматирование L0–L3 вывода.
8. **Выходы и адаптеры**: выдача объявленных `output` в собственной модели runtime; преобразование во внешние форматы выполняют необязательные host-адаптеры.

## 4. Модель данных

### 4.1. Геометрия

Геометрия = **топология + таблицы атрибутов по доменам**. Единая модель для всех типов; никаких параллельных концепций «поле vs атрибут» (см. 4.4).

**Домены:**

| Домен | Смысл |
|---|---|
| `points` | вершины/точки (позиции, основной рабочий домен) |
| `corners` | углы полигонов (UV, per-face нормали) |
| `faces` | полигоны/примитивы |
| `edges` | рёбра |
| `detail` | одно значение на всю геометрию (общий seed, центроид, число островов) |

**Типы значений атрибутов:** `f32`, `int`, `bool`, `vec2`, `vec3`, `vec4`, `string`. `int` — знаковое 64-битное целое языка; правила переполнения фиксируются численным контрактом runtime. Встроенные атрибуты: `@P` (vec3, точки), `@N` (vec3, точки), `@index` (int, любой домен — номер элемента в домене).

**Цвет поверхности — `@Cd` (v1.17).** Канонический атрибут цвета: `vec3`, линейный RGB в `[0, 1]`, любой домен (`faces` — «покраска по материалам», `points` — градиенты/шум, `corners` — жёсткие швы). Имя зарезервировано: `set(g, "Cd", …)` не требует `typeinfo` (тег `none`, `transform` не трогает). Пишется обычным `set` — цвет есть поле, как и форма: `set(g, "Cd", ingroup("stone") ? mix(c_dark, c_light, fbm(…)) : c_wall, domain = faces)`. Читатели: PggViewer (чекбокс «colors (@Cd)», faces/corners размораживают сварку, чтобы цвет грани не растекался на соседей), `PggTool run --obj` (`v x y z r g b`, faces/corners → развёрнутый меш). `color` и `tint` — тоже зарезервированы без тега, но не канон: `@tint` — **множитель** стампа инстансов (`instance_on_points`/`realize`, §8.8; на реализованном меше живёт на points, дефолт и нейтраль в `merge` — белый), `color` — свободное имя без семантики для инструментов. Неокрашенная геометрия у читателей — нейтрально-серая; в авторском коде рекомендуемая идиома для «граней вне всех групп» — маркерный цвет (пурпур), а не материал: незакрашенное должно быть видно.

**Материальные атрибуты (v1.24).** Кроме цвета зарезервированы (тип f32, тег `none`, статически типизированы при чтении `@ao`/`@roughness`): `@ao` — запечённая ambient occlusion `[0, 1]` (пишет `bake_ao`, §8.9; читатели умножают на неё `@Cd`; нейтраль в `merge` — 1, «открыто»), `@roughness` — шероховатость `[0, 1]` (0 — зеркало, 1 — матовое; конвенция для будущего рендера/экспорта: сейчас превью её не читает, но `merge`-нейтраль — 0.7, и имя не занять под другое). Нейтраль `@Cd`/`color` в `merge` — нейтральный серый читателей `(0.66, 0.64, 0.61)`, а не ноль: нераскрашенный операнд рядом с раскрашенным раньше становился чёрным.

**Typeinfo — геометрический смысл атрибута (v1.14, по образцу Houdini).** У каждой колонки, помимо типа значения, есть тег `typeinfo ∈ {none, vector, normal, point, quaternion}`, который говорит `transform`/`realize`, **как** двигать колонку вместе с геометрией (по имени узлы ничего не угадывают):

| typeinfo | Смысл | `transform(translate, rotate, scale)` / стамп инстанса |
|---|---|---|
| `none` | данные (цвет, размер, id) | копируется как есть |
| `vector` | направление с длиной | `rot · (v · scale)` — без переноса |
| `normal` | нормаль поверхности | inverse-transpose (`rot · (n / scale)`), ренормализация |
| `point` | позиция | полная аффинная: `rot · (p · scale) + translate` |
| `quaternion` | ориентация `(x, y, z, w)` | композиция `q' = rot · q` |

Тег ставит `set(..., typeinfo = ...)`; при `auto` вывод разрешён только там, где двусмысленности нет: зарезервированные имена (`N` → normal, `orient` → quaternion, `tint`/`color`/`Cd` → none) и все не-векторные типы (`f32`/`int`/`bool`/`vec2`/`string` → none). **Любой `vec3`/`vec4` под свободным именем обязан нести явный `typeinfo` — иначе E610** (направление, позиция или цвет — решает автор, а не эвристика: молчаливый дефолт в любую сторону воспроизводил бы исходный баг «атрибут не поехал / поехал не тот»). E610 также: тег не совпадает с типом значения (`vector`/`normal`/`point` требуют vec3, `quaternion` — vec4); зарезервированный стамп инстанса записан не своим типом (`orient` — vec4, `tint` — vec3, `scale` — f32, `variant` — int) или `orient` — не quaternion. Проверяется статически (литеральное имя + известный тип значения) и в рантайме. Builtin'ы тегируют свои выходы сами (`compute_normals(mode = flat)` → corner-`N` normal; `transform` на инстансах материализует `@orient` quaternion). Тег едет с колонкой через `promote`/`rename_attr`/`distribute_points`/`merge`/`realize`/`fracture` и входит в фингерпринт (кэш различает `typeinfo = vector` и `none`). В `merge` одноимённые колонки обязаны совпадать тегом (E609, §8.3), а нейтральный заполнитель отсутствующей стороны берётся по тегу: `quaternion` → единичный кватернион, `normal` → нормали, выведенные из граней, прочие → ноль. Встроенный `@N` всегда `normal`; `@P` — `point`.

**Производный `@N` (v1.14).** Если у меша нет сохранённой колонки `@N`, чтение `@N` на любом домене отдаёт нормаль, выведенную из топологии (points — сумма нормалей инцидентных граней, corners/faces — нормаль грани, detail — среднее): `set_position(mesh_from_sdf(...), offset = @N * k)` работает без `compute_normals`, атрибутный барьер §8.4 при этом не нарушен — колонка не создаётся. Сохранённый `@N` (источники, `compute_normals`) остаётся авторитетом. У геометрий без граней (`points`, `instances`) `@N` по-прежнему E302.

**Устаревший `@N` (W006).** Сохранённая колонка не пересчитывается сама: после `set_position`/`smooth` она описывает прежнюю поверхность. Чтение `@N` на такой геометрии без промежуточного `compute_normals` — предупреждение **W006** (статически, по флагу схемы; `merge` наследует флаг от любого операнда). Выходы: `compute_normals(g)` после смещения, либо `remove_attr(g, "N")` — снимает **и** выделенную колонку нормалей, после чего меш читает свежие производные нормали. Меш, у которого колонки не было (`mesh_from_sdf`), устареть не может.

**Виды геометрии (`GeoKind`) и домены атрибутов — разные оси типовой системы.** Вид отвечает на вопрос «какая топология у значения целиком», домен — «сколько значений в колонке атрибута и к каким элементам они привязаны». Они не конвертируются друг в друга и записываются в разных синтаксических позициях.

Первоклассный тип геометрии — `geo<K>`, где `K` — один из видов:

- `geo<mesh>` — полигональная сетка;
- `geo<points>` — облако точек без связности (носитель для инстансинга и разброса);
- `geo<curve>` — кривые (пост-MVP: корни, трещины);
- `geo<instances>` — лёгкие копии исходной геометрии на точках; материализуются только явной операцией `realize`.

Голый `geo` в сигнатуре означает полиморфное «любой `geo<K>`»; конкретный `K` сохраняется, если контракт узла явно не меняет вид. `sdf` — отдельный первоклассный тип неявной геометрии (воксельное или аналитическое поле), не подтип `geo`: у него нет таблиц атрибутов и доменов до извлечения поверхности. **Это основной рабочий тип для органики**: сглаженные булевы операции и шумовой дисплейс в SDF не рвут топологию.

В сигнатурах каталога запись `geo<K>` с одной и той же переменной `K` означает сохранение конкретного вида: например, `merge<K>(geo<K>, geo<K>) -> geo<K>` принимает два одинаковых вида и возвращает тот же вид. Это метанотация спецификации builtin'ов, не дополнительный синтаксис пользовательских `def`.

### 4.2. Группы (именованные маски)

Маска — булево поле. **Группа — именованная маска, живущая на геометрии** (аналог групп в Houdini). Создаётся операцией `mark`, читается по имени, комбинируется логикой. Маски накапливаются на геометрии и переиспользуются на любом удалении по пайплайну — это основной механизм «памяти» процедурного моделирования.

### 4.3. Атрибуты — хранилище

Атрибуты материализованы и принадлежат геометрии. Запись — только через `set(geo, name, field)`. Чтение — через `@name` в выражениях. При чтении атрибута с «чужого» домена выполняется **молчаливая интерполяция** по правилам доменов (faces→points — усреднение по инцидентным, points→faces — по вершинам и т.д.); явный контроль — операцией `promote` с указанием режима (`sum`, `average`, `first`).

### 4.4. Поля — выражения над хранилищем

**Поле (`field<T>`) — ленивая функция от элемента геометрии, а не данные.** Это центральная концепция системы:

- Узел `fbm(...)` не вычисляет шум в точке определения — он возвращает *функцию шума*, которая будет вычислена **в точке потребления**, per-element, для той геометрии, которая пришла в узел-потребитель.
- Контекст вычисления определяется **потребителем**, а не производителем: одно и то же ребро с `@P` означает разные значения в разных местах графа.
- Для `sdf` «элемент» контекста — **точка сэмплирования поля**: `@P` внутри поля, вычисляемого над sdf, — позиция сэмпла в пространстве, а не вершина меша.
- Поля композиционны: `@N * fbm(...) * 0.35` — поле, собранное из полей.
- Материализация поля происходит: при записи в атрибут (`set`), в агрегаторе, в инспекторе, при свёртке в значение любым узлом, принимающим конкретные данные.

**Правило идентичности:** поле memoizируется по ключу `(поле, контекст геометрии)`. Одно поле, идущее в три потребителя на одной геометрии, вычисляется один раз.

### 4.5. Значения vs поля

Типовая система различает `T` (значение) и `field<T>` (поле) — это видно в сигнатурах и в языке. Мосты между мирами:

- **поле → значение:** только явной редукцией — агрегаторы (`average`, `min`, `max`, `count`, `sum`), сэмплинг (`sample`), геометрические сводки (`bbox`, `centroid`, `extent`). Без агрегаторов целый класс задач («отнормировать дисплейс на размер баундинг-бокса») невыразим.
- **значение → поле:** неявно, константным полем.

**Неявные конверсии значений** (numpy-стиль, применяются и внутри полей): `bool → int → f32`; скаляр → вектор (broadcast); векторная арифметика — покомпонентная. Обратные сужающие конверсии — только явными кастами `int(x)`, `bool(x)` (§6.3).

`rng` — отдельное непрозрачное immutable-значение, разрешённое в bindings и сигнатурах `def`. Оно не является атрибутом, не преобразуется в число, а тип `field<rng>` запрещён. Сам `rng` можно захватить как value-вход выражения, возвращающего числовое поле; создаётся он только операциями §5.2/§8.5.

## 5. Семантика вычислений

### 5.1. Граф и порядок исполнения

- Граф — DAG. Ребро = определение и использование имени (см. §6). Топологический порядок совпадает с порядком строк сверху вниз.
- Исполнение **pull-based**: движок тянет от явно объявленных `output` верхнего уровня (§6.7) и запрошенных пробников, вычисляя только необходимые подграфы.
- Геометрия иммутабельна: каждый узел производит новую геометрию, шаринг неизменённых данных (structural sharing) — обязателен.
- Per-element вычисления полей параллелятся; воспроизводимость (N1) обязывает: порядок суммирования в агрегаторах фиксирован (по `@index`), случайные значения выводятся из явного `rng` и семантического счётчика элемента, а не из порядка исполнения потоков.

### 5.2. Воспроизводимость и модель генераторов

`seed` — только исходное число для создания генератора; стохастические узлы принимают не голый seed, а значение типа **`rng`** — неизменяемый воспроизводимый генератор случайной последовательности:

```text
param world_seed: int

world_rng = rng_from_seed(world_seed)
rocks_rng = split_rng(world_rng, key = "rocks")
```

- `rng_from_seed(seed: int) -> rng` создаёт корневой генератор.
- `split_rng(parent: rng, key: int) -> rng` и `split_rng(parent: rng, key: string) -> rng` — две встроенные перегрузки, чисто и детерминированно создающие независимый дочерний генератор. Вызов не изменяет `parent`; одинаковые `parent` и `key` одного типа всегда дают один и тот же `rng`.
- У каждой стохастической операции параметр `rng: rng` **обязательный** и без неявного дефолта. Один и тот же `rng` с теми же входами намеренно воспроизводит ту же последовательность независимо от места вызова. Для независимой вариации автор явно вызывает `split_rng`; для задекларированного намеренного повтора — `alias_rng` (§8.5, линт §6.5).
- Внутри генератор реализован как counter-based PRNG: случайное слово адресуется кортежем `(generator_key, counter, lane)`, а не последовательным `next()` и не состоянием потока исполнения. Per-element random-узлы по умолчанию используют `@index` как `counter`, номер компоненты как `lane`; алгоритмические узлы фиксируют свою схему адресации в ABI-контракте. Поэтому параллельный порядок вычисления не меняет случайные значения.
- В `repeat` один и тот же `rng` на каждой итерации воспроизводит одну и ту же последовательность. Если итерациям нужна стабильная вариативность, она выражается явно:

  ```text
  iter_rng = split_rng(sim_rng, key = @iteration)
  ```

  Аналогично, автор явно вызывает `split_rng(parts_rng, key = @piece_index)` внутри `foreach`. Валидатор предупреждает, если стохастический узел внутри `repeat` получает генератор, не зависящий от `@iteration`, или внутри `foreach` — от `@piece_index`: это допустимый намеренный повтор, но частый источник ошибки.
- Никакой неявной соли по instance path или позиции вызова нет. Перенос вызова, переименование SSA-binding или вставка соседнего вызова не меняют случайную последовательность. Instance path остаётся только адресом диагностики (§7.7).
- Генератор чанка выводится явным иерархическим split:

  ```text
  chunk_x_rng = split_rng(world_rng, key = chunk_x)
  chunk_rng   = split_rng(chunk_x_rng, key = chunk_y)
  ```

  Чанки можно вычислять независимо и в любом порядке; одинаковые координаты получают одинаковую случайную последовательность.
- **Граница стабильности рандома.** Per-element random-узлы по умолчанию используют текущий `@index`; правки, меняющие число или порядок элементов выше по потоку (`delete`, другой `subdiv`), законно переставляют значения ниже по потоку. Когда идентичность должна переживать такие правки, автор передаёт сохранённый стабильный атрибут явно: `random(..., counter = @id, rng = ids_rng)`.
- Алгоритмы `rng_from_seed`/`split_rng`, domain separation, кодирование знакового `int` и строки-ключа, а также преобразование случайных слов в `f32` фиксируются версией языка. Для одинакового `(generator_key, counter, lane)` случайное слово должно быть бит-в-бит одинаково на всех поддержанных платформах; это более узкая гарантия, чем битовая идентичность всей float-геометрии (§2, N1).
- **Numeric profile** входит в отчёт запуска и ключ кэша. Его идентичность включает backend, target ISA, compiler и значимые flags, FP mode, math library, версии численных алгоритмов и runtime build. Внутри одного profile операции обязаны иметь фиксированный порядок, агрегации — фиксированный порядок обхода, а параллельное планирование не должно менять результат. Между разными CPU/GPU, компиляторами и профилями допустимы различия последних битов float и, у пограничных случаев topology-changing операций, различия дискретного результата. Такие сравнения проверяются допусками и геометрическими инвариантами, а не равенством бинарного хэша.
- **Межмашинный паритет мира (продуктовая оговорка).** Если продукту когда-нибудь понадобится генерация идентичного мира на разных машинах (клиент и сервер строят одни и те же чанки), одной битовой стабильности случайных слов недостаточно: дискретные решения (маски `>`, приёмка poisson-кандидатов, знак изо-пересечения) могут разойтись между numeric profiles на граничных float-значениях. Для такого режима дискретные решения переводятся на целочисленную адресацию — отдельный контракт; в MVP не требуется.
- Язык не требует собственной корректно округлённой реализации всех трансцендентных функций и не обещает CPU↔GPU bit-for-bit. Узел, для которого межплатформенная устойчивость критична, обязан документировать более сильный контракт отдельно.

### 5.3. Кэширование и инкрементальность

- Ключ кэша узла/экземпляра def: `hash(структура подграфа, значения параметров, идентичности rng, версии входных результатов, numeric_profile_id)`.
- Правка файла: dirty-propagation от изменённых определений вниз по потоку; незатронутые подграфы берутся из кэша (N4).
- Кэш инспекторов отдельный: включение отладки не сносит продакшен-кэш.

### 5.4. Итеративные процессы: зоны

Чистый dataflow ацикличен и не выражает накопление состояния (эрозия, рост, релаксация, итеративное сглаживание). Для этого — ровно два конструкта, оба с **явной передачей состояния через интерфейс** (тело остаётся чистым графом). Синтаксис зон — фигурные скобки, как у всего языка (§6.2.4).

**`repeat` — fold по итерациям:**

```text
# flow_direction/erode_step — библиотечные def'ы (иллюстративные), не встроенные узлы
eroded = repeat(terrain, iterations = 50) |state| {
    water = flow_direction(state)
    state = erode_step(state, water, rate = 0.02)
}
```

Семантика: имена состояния зоны объявляются в заголовке (`|state|`, допустимо несколько: `|a, b|` — тогда и выходов у зоны столько же, деструктуризация как у def). Это парные порты границы зоны, а не изменяемые переменные: в начале итерации `state` читается как входной порт, а единственное допустимое определение `state = ...` в теле связывает соответствующий выходной порт. Для каждого имени состояния такое связывание обязательно и допускается ровно один раз; промежуточные шаги получают отдельные SSA-имена. Выход итерации N−1 подаётся на вход итерации N; при `iterations = 0` внешним выходом становится исходный вход. Тело остаётся обычным SSA-графом, в IR одно исходное имя разворачивается в разные входной и выходной порты; снаружи зона — обычный узел: входы → выходы. Итерации материализуются. В теле доступна константа `@iteration` (int, 0-based) — см. §6.3.

**`foreach` — map по связным компонентам:**

```text
sites_rng = split_rng(world_rng, key = "fracture_sites")
cut_rng   = split_rng(world_rng, key = "fracture")
parts_rng = split_rng(world_rng, key = "parts")
sites     = point_cloud(count = 12, bounds = (10, 1, 10), rng = sites_rng)
fractured = fracture(rock, planes = sites, rng = cut_rng)
chunks    = foreach piece in fractured {
    piece_rng  = split_rng(parts_rng, key = @piece_index)
    jitter_rng = split_rng(piece_rng, key = "jitter")
    noise_rng  = split_rng(piece_rng, key = "surface")
    # per-element джиттер (counter = index() по умолчанию); для uniform-сдвига всего куска — counter = 0
    point_jitter = random_vec(lo = (-0.1, -0.1, -0.1), hi = (0.1, 0.1, 0.1), rng = jitter_rng)
    displaced  = set_position(piece, offset = fbm(@P, scale = 3, rng = noise_rng) * 0.1 + point_jitter)
    piece      = smooth(displaced, iterations = 2)
}
```

Семантика: вход разбивается на связные компоненты (или уже размеченные куски), тело применяется к каждой независимо, результаты объединяются (жёсткий merge, без сварки). Состояние между кусками не течёт ⇒ идеально параллелится. В теле доступна константа `@piece_index` (int) — ключ для явного выделения per-piece генератора; `@index` внутри тела по-прежнему означает индекс элемента внутри куска.

**`foreach` по `geo<points>` — «модель строк» (v1.20).** Коллекция может быть и облаком точек: тогда кусок — **одна точка** со всеми её атрибутами/группами (detail разделяется), порядок кусков = `@index`, `@piece_index` = номер точки. Это декларативный аналог QML `Repeater { model: ... }`: точки — модель, тело — делегат; per-элементные данные (длина ряда, сдвиг, вариант) живут атрибутами модели и читаются агрегатором `value(@attr, on = row)` (§8.10) — единственный элемент, значение в собственном типе поля. Тело обязано вернуть в item-порт `geo<mesh>` или `geo<points>` (kind может отличаться от входного — строка-точка часто становится мешем), все куски одного kind (иначе E607); тип target'а = тип item-порта после тела. Внутри одноточечного куска `@index` **всегда 0** — номер строки берётся из `@piece_index` или из атрибута модели. `geo<instances>` как коллекция — E204 (сначала `realize`, либо итерируй якоря).

```text
# ряды кладки: модель — точки-ряды, у каждого свои n и сдвиг перевязки
rows0 = mesh_line(count = 6, length = 5.0 * 0.26, dir = (0, 1, 0))
rows  = set(rows0, "n", 8 - (@index - 2 * (@index / 2)), domain = points)   # чёт 8 / нечет 7
wall  = foreach row in rows {
    n       = value(@n, on = row)
    anchors = mesh_line(count = n, length = f32(n - 1) * 0.5, dir = (1, 0, 0))
    row     = stone_course(anchors, at = value(@P, on = row), shift = f32(@piece_index - 2 * (@piece_index / 2)) * 0.25)
}
```

**Def'ы и зоны сочетаются свободно (v1.20).** Вызов def внутри тела зоны — обычный узел тела: экспансия инлайнит его как один статический инстанс на call-site, исполняемый на каждой итерации/куске; контракты `expect`/`ensure` инстанса срабатывают на каждой итерации. Зона внутри тела def клонируется в каждый инстанс def'а (имена зоны — targets, порты, тело — переименовываются под instance path, как остальные локальные имена). Вложенность в обе стороны не ограничена: def с `foreach` внутри, вызванный в `foreach`, — штатный способ «ряды × элементы в ряду».

**Связывание выходных портов зоны — единственное санкционированное пограничное связывание поверх SSA** (§6.2.1): имя из заголовка доступно на чтение как входной порт и ровно один раз определяется в теле как выходной порт того же **логического канала состояния**. Это не переприсваивание и не две ноды с одним именем: в IR вход и выход имеют разные идентификаторы, а общее исходное имя обозначает их пару на границе зоны. В нодовой проекции зона — подграф с портами «вход итерации» / «выход итерации», соединёнными петлёй провода (как begin/end в for-each подсетях Houdini). Каждая итерация/кусок — свежая инстанциация области видимости; все промежуточные имена в теле остаются уникальными по общему правилу.

Рекурсия def'ов **запрещена** (см. §7.6) — зоны единственный механизм итерации.

## 6. Язык: правила записи

Проектный принцип: **язык оптимизирован под генерацию и самокоррекцию LLM-агентом**, человек — второй читатель. Отсюда жёсткие правила единственности форм.

### 6.1. Связи: ребро — это имя

Никаких конструкций `connect(a.out, b.in)`. Связь = определение и использование имени:

```text
root_rng  = rng_from_seed(42)
noise_rng = split_rng(root_rng, key = "surface")
base = ico_sphere(subdiv = 3, radius = 1.0)
n    = fbm(scale = 2.5, octaves = 5, rng = noise_rng)
rock = set_position(base, offset = @N * n * 0.35)
```

Граф восстанавливается из текста автоматически. Нодовая проекция — рендер этого графа.

### 6.2. Шесть базовых правил

1. **SSA.** Каждое имя определяется ровно один раз в своей области видимости. «Изменение» = новое имя (`rock`, `rock_smooth`, `rock_final`). Переопределение запрещено — **имя это нода, а двух нод с одним именем в графе не существует**. Единственное специальное правило — связывание выходного порта состояния зоны (§5.4): имя из заголовка читается как входной порт и ровно один раз определяется как парный выходной порт; в IR это разные идентификаторы одного граничного канала, а не переприсваивание.
2. **Define-before-use.** Ссылаться можно только на имена, определённые выше по тексту. Циклы невозможны синтаксически; порядок чтения = порядок вычисления.
3. **Один канонический вид записи:** `имя = операция(аргументы)`. Запрещены альтернативные нотации: пайп-цепочки, метод-синтаксис, префиксная запись. Математику внутри аргументов можно инлайнить (`@N * n * 0.35`), структуру — только именованными шагами.
4. **Синтаксис — C-family для структуры, питоноподобный для мелочи.** Блоки — фигурными скобками (`def`, зоны repeat/foreach); keyword-аргументы, комментарии `#`. Обоснование: (а) первичный автор — LLM, а скобки переживают машинные патчи и транспорт через JSON/чаты: ведущие пробелы невидимы, их потеря ломает парсинг до того, как сработает форматтер, скобочный же текст парсится при любых отступах; (б) ошибки скобок локализуются точно («открыта `{` в строке 12»), ошибки отступов — почти никогда (N6); (в) ближайшие доменные аналоги в обучающих данных — GLSL/HLSL/VEX — скобочные.
5. **Мультивыходы — деструктуризация в месте вызова:**
   ```text
   cliffs, flats = split(rock, mask = @slope > 0.5)
   ```
6. **Герметичность.** Нет неявных глобалов, «сцены», «выделенного объекта», автоподгружаемого prelude. Всё, что использует узел, приходит через аргументы; все источники имён видны в тексте файла (импорты и внешние параметры `param` — явные, см. §6.6). Следствие: сгенерированный кусок исполняется и тестируется изолированно.

### 6.3. `@`-выражения

Математика и чтение атрибутов — инлайн-выражения в аргументах (ноды — для структуры, выражения — для математики):

```text
root_rng    = rng_from_seed(42)
mask_rng    = split_rng(root_rng, key = "mask")
surface_rng = split_rng(root_rng, key = "surface")
mask = (@slope > 0.4) & (fbm(scale = 6, rng = mask_rng) > 0.3)
disp = @N * fbm(@P * 2.5, octaves = 5, rng = surface_rng) * 0.35
```

`@name` читает атрибут как поле. **Статический тип чтения** (v1.23): встроенные и зарезервированные/конвенционные имена типизированы (`@P`/`@N`/`@Cd`/`@color`/`@tint` — vec3, `@orient` — vec4, `@uv`/`@profile_scale` — vec2, `@index`/`@variant`/`@island_id` — int, `@scale`/`@twist`/`@t` — f32), прочие пользовательские имена — **неизвестного типа**: выражение над ними типизируется разрешающе (`dot(@col, up)`, `length(@v)`, `int(@k)` проходят typecheck), а точная проверка тех же правил выполняется в рантайме по фактической колонке (E204 с пометкой «actual attribute types»). До v1.23 пользовательский атрибут условно считался f32, и `dot(@Cd, …)` статически падал с E204. Операторы: арифметика, сравнения, `&` `|` `!`, тернарный `cond ? a : b` (GLSL-форма, единый вид с остальными выражениями), `ramp(x, points...)`. Встроенные функции выражений: `dot/cross/length/normalize/clamp/smoothstep/mix/abs/min/max/floor/pow`, вещественная математика (v1.22) `sin/cos/tan/asin/acos/atan/atan2(y, x)/sqrt/exp/log/ceil/round/fract/mod(a, b)/radians/degrees` — аргументы в **радианах** (углы в градусах — через `radians(x)`; `transform`/`orient_from_euler` при этом принимают градусы), `int` продвигается в `f32`, векторы покомпонентно, `bool` — E204, `mod` — GLSL-семантика `a − b·floor(a/b)` (знак делителя; целочисленный остаток — оператор `%`), `round` — от нуля (`round(2.5) = 3`); конструкторы `vec2(x, y)` / `vec3(x, y, z)` / `vec4(...)`, касты `int(x)` / `f32(x)` / `bool(x)`, ориентация `orient_from_euler(rot: field<vec3>) -> field<vec4>` (Эйлер, градусы → кватернион (x, y, z, w)) — способ авторинга `@orient` для инстансинга (§8.4, §8.8). Выражение компилируется в подграф полей — семантически это сахар, в AST — узлы.

Правила конверсий — §4.5 (bool→int→f32, broadcast скаляра в вектор, покомпонентная векторная арифметика). Векторный литерал `(0, 0, 1)` — только из числовых констант, компоненты могут быть со знаком (`(-0.5, 0, 1)` — валидный vec3); вектор из вычисленных значений собирается `vec3(x, y, z)`. Литерал обязан содержать хотя бы одну запятую: `(1)` и `(-1)` — скалярные выражения в скобках, а не vec1 (векторные литералы — vec2..vec4).

Два особых `@`-имени: **`@iteration`** (в теле `repeat`) и **`@piece_index`** (в теле `foreach`) — это константы-**значения** (int), предоставляемые зоной, а не поля; их можно использовать как ключи `split_rng`. Это единственные `@`-имена со value-семантикой.

### 6.4. Форматтер

Канонический форматтер обязателен и применяется к любому файлу перед коммитом/прогоном: отступы 4 пробела, открывающая скобка на строке заголовка (K&R), закрывающая — на своей строке, один `=` с пробелами, keyword-аргументы в объявленном порядке, trailing comma в многострочных вызовах. Цель — минимальные diff'ы между версиями от LLM.

### 6.5. Линт (предупреждения)

- определённое, но не использованное ниже имя (симптом недописанной цепочки);
- стохастическая операция без явного traceable `rng`;
- один `rng` (с учётом SSA-алиасов) питает два и более стохастических узла — вероятная нежелательная корреляция: независимость оформляется `split_rng`, намеренный повтор декларируется `alias_rng` (§8.5); предупреждение не срабатывает на генераторы, прошедшие через `alias_rng`. **Заметка реализации (A1, v1.8):** реализовано как W003; покрывает встроенные стохастические операции (`fbm`/`vnoise`/`random`/`random_vec`/`random_int`/`point_cloud`/`distribute_points`), но не def-вызовы — один `rng` на двух def-инстансах остаётся легальной идиомой намеренного повтора §7.3 (модель идентичности генератора и мотивы скоупа — в §19 v1.8);
- стохастическая операция внутри `repeat`, чей `rng` не зависит от `@iteration` (предупреждение: допустимый, но подозрительный намеренный повтор);
- стохастическая операция внутри `foreach`, чей `rng` не зависит от `@piece_index` (то же предупреждение);
- группа создана и нигде не читается;
- def без docstring-контракта (в библиотечных файлах — ошибка; библиотечный файл = файл в корнях импорта движка, см. §7.6).

### 6.6. Внешние параметры файла (`param`)

Все входы, которые файл получает извне, объявляются явно в начале файла (после импортов, до использования):

```text
param world_seed: int
param chunk_x: int = 0
param chunk_y: int = 0
```

Движок привязывает значения при запуске (`engine run rock.pgg --param world_seed=42`). Параметр без дефолта, не привязанный при запуске, — ошибка E604. Обращение к имени, не объявленному ни как binding, ни как param, ни как импорт, — ошибка разрешения имён (герметичность, §6.2.6). Дефолты параметров — только константы (литералы, enum- и домен-литералы), не ссылки на другие имена.

### 6.7. Выходы файла (`output`)

Pull-граф обязан иметь явные корни. Исполняемый файл помечает уже определённые top-level bindings:

```text
root_rng    = rng_from_seed(42)
rock_rng    = split_rng(root_rng, key = "rock")
scatter_rng = split_rng(root_rng, key = "scatter")
final_mesh = make_rock(rng = rock_rng)
anchors    = distribute_points(final_mesh, density = 2, rng = scatter_rng)

output final_mesh
output anchors
```

- `output` не создаёт новую ноду и не переименовывает значение; это экспортируемый корень вычисления.
- Имя должно быть определено выше на верхнем уровне, не внутри `def` или зоны. Повторное объявление одного имени — ошибка.
- Файл, запускаемый как граф, обязан иметь хотя бы один `output`; иначе E605. Библиотечный модуль, содержащий только определения `def`, может не иметь выходов.
- `tap` не является выходом: при `debug=off` диагностический слой удаляется, но семантические корни остаются.
- CLI может запросить подмножество объявленных выходов (`--output final_mesh`); без флага вычисляются все `output`.
- Binding, объявленный как `output`, считается использованным для линта (§6.5).
- Допустимые корни: `geo<K>`, `sdf` и обычные value-типы (`f32`, `int`, `bool`, векторы, `string`). Голое контекстное `field<T>` и служебный `rng` экспортировать нельзя.

## 7. Композиция: супер-узлы (def)

Механизм «из простых узлов строить составные и использовать как узлы» — аналог функций в программировании и супер-состояний в стейт-машинах. Встроенные узлы и def **неотличимы на вызове**: `fbm(...)` и `fbm_displace(...)` — один синтаксис. Конечная цель — стандартная библиотека, написанная на самом языке: движок даёт ~35 примитивов, всё остальное — def'ы поверх них.

### 7.1. Сигнатура = интерфейс узла

```text
def fbm_displace(geo: geo, scale: f32 = 2.5, amp: f32 = 0.35, rng: rng) -> (out: geo) {
    """Дисплейс слоистым шумом вдоль нормалей.
    Требует: @N на точках. Пишет: @disp (f32, точки).
    Пример: rock = fbm_displace(base, amp = 0.2, rng = detail_rng)
    """
    n         = fbm(scale = scale, octaves = 5, rng = rng)
    displaced = set_position(geo, offset = @N * n * amp)
    out       = set(displaced, "disp", n * amp)
}
```

- **Выходы — имена, объявленные в сигнатуре.** Тело обязано определить ровно эти имена (ровно один раз каждое — общее правило SSA); `return` отсутствует. Мультивыходы: `-> (steep: geo, flat: geo)`, вызов — той же деструктуризацией, что и у встроенных узлов. Один механизм на всех уровнях.
- **Дефолты в сигнатуре** — это «слайдеры» узла; сигнатура с дефолтами — самодокументируемый API.
- **Сигнатура — полный список ручек.** Внутренние константы снаружи недоступны; настраиваемость = поднять параметр явно.

### 7.2. Передача полей через границу

- Геометрия передаётся по значению (иммутабельна — шаринг бесплатен).
- **Поле передаётся лениво и вычисляется в контексте внутри def** — замыкание, разворачивающееся на геометрии, пришедшей в тело:

```text
def displace(geo: geo, amount: field<f32>) -> (out: geo) {
    out = set_position(geo, offset = @N * amount)
}

rock = displace(base, amount = fbm(scale = 2.5, rng = detail_rng) * @height_rel)
```

`@height_rel` ищется на геометрии в месте вычисления; отсутствует — ошибка контракта (ловится статически, см. 7.6). Сигнатура `amount: field<f32>` — контракт «дай любую функцию от элемента».

### 7.3. RNG-дисциплина

- В теле def есть стохастика, а в сигнатуре нет входа типа `rng` — **ошибка компиляции**. Генератор обязан явно течь по сигнатуре.
- Стохастичность вычисляется валидатором **транзитивно по DAG вызовов def** (рекурсия запрещена ⇒ вычислимо): def, вызывающий стохастический def или встроенный рандом-узел, сам считается стохастическим и обязан принимать `rng`.
- Скрытого split по instance path нет. Если def нужно несколько независимых последовательностей, он явно создаёт их через `split_rng`; одинаковый входной `rng` намеренно воспроизводит тот же результат.
- Переиспользование одного генератора несколькими стохастическими узлами — легальный намеренный повтор, но линт предупреждает о нём как о частой ошибке корреляции (§6.5): намерение фиксируется явным `alias_rng` (§8.5), независимость — `split_rng`.

### 7.4. Контракты: expect/ensure

```text
def erode(terrain: geo, iterations: int = 50, rng: rng) -> (out: geo) {
    expect terrain has @height: "erode работает с хайтфилдом, см. make_heightfield"
    expect iterations > 0: "число итераций — положительное"
    ...
    ensure out has @wetness
}
```

Две формы: проверка наличия атрибута (`expect имя has @attr`) и проверка произвольного условия над значениями параметров (`expect выражение`). `expect/ensure` — проверки валидатора, а не комментарии. **Текст ошибки пишет автор def'а — для нейронки**: валидатор отвечает не «attribute missing», а готовой подсказкой, какой def вызвать перед этим. Библиотека самонаводящаяся: каждый def знает свои требования и умеет объяснить, как их удовлетворить.

### 7.5. Документация как данные

Docstring — часть ABI: первое предложение — что делает; блок «Требует/Пишет» — контракт атрибутов; пример вызова. Tooling: `engine docs lib.rocks.make_rock` выдаёт карточку def'а. LLM перед генерацией запрашивает доки нужных узлов — главный источник знаний о библиотеке вместо галлюцинаций.

### 7.6. Импорты, запрет рекурсии

```text
import lib.noise
import rocks.basic as rb

root_rng  = rng_from_seed(42)
noise_rng = split_rng(root_rng, key = "noise")
rock_rng  = split_rng(root_rng, key = "rock")
n    = noise.fbm(at = @P, rng = noise_rng)
rock = rb.make_rock(size = 2, rng = rock_rng)
```

- Файл = модуль; импорт явный; prelude запрещён; каждое имя статически разрешимо из текста.
- Импорт всегда связывает **namespace**, а не подмешивает имена в текущую область. Без `as` именем namespace становится последний компонент пути (`lib.noise` → `noise`); `as rb` задаёт его явно. Вызов импортированного символа всегда квалифицирован: `noise.fbm(...)`, `rb.make_rock(...)`.
- Два импорта не могут связать один namespace; namespace не может конфликтовать с `param`, top-level binding, top-level `def` или встроенной операцией. Неизвестный qualified symbol — E505.
- Из импортированного модуля видны его top-level `def`; `param`, обычные bindings, `output` и диагностические инструкции принадлежат экземпляру исполняемого файла и через namespace не экспортируются.
- Тело `def` герметично относительно runtime-значений модуля: оно не может захватывать top-level `param`, `rng` или обычный binding. Свободными именами в теле могут быть только встроенные операции и квалифицированные/локальные `def`; все значения передаются через сигнатуру.
- Корни импорта задаются конфигурацией движка (например, каталог `lib/` стандартной библиотеки + каталог текущего файла). Файл в корне импорта считается **библиотечным** — к нему применяются усиленные требования линта (§6.5).
- **Рекурсия def'ов запрещена.** Следствия: полная статическая экспансия; **статический вывод схемы сквозь границы def** (валидатор проталкивает множества атрибутов и ловит «`@height_rel` отсутствует здесь» до запуска — включая атрибуты, на которые ссылаются поля-замыкания, переданные аргументами: при полной экспансии поле инлайнится в контекст вызова и проверяется там); кэш на границах по ключу (def, аргументы, `rng`); правка def инвалидирует только его экземпляры.
- Переименование выхода = ломающее изменение сигнатуры; валидатор библиотеки сравнивает сигнатуры между версиями. Версионирование импортов `import rocks.cliff @1.2` — опционально, на старте не реализуется.

### 7.7. Адресация экземпляров (instance path)

Имена внутри def адресуются путём экземпляра:

```text
world.cliff_wall[0].make_rock[3].n
```

Instance path используется для пробников (§9.4), стеков ошибок (§11.2) и навигации «провалиться внутрь супер-узла» в проекции (§10), но не влияет на случайные последовательности (§5.2).

## 8. Стартовый каталог встроенных узлов

MVP-набор: ~35 узлов, покрывающих сценарий §1.3 целиком. Всё остальное строится def'ами поверх. Для каждого узла: сигнатура, что делает с геометрией, что пишет/читает. Значения enum-параметров объявляются инлайн в сигнатуре (`mode: enum {smooth, flat} = smooth`) — валидатор проверяет принадлежность статически (E206). Машиночитаемая форма каталога — `PggTool docs builtins [--group <секция>]` (сигнатуры из живого реестра) и `PggTool docs builtin <имя>` (сигнатура + абзац + пример); RPC вьювера — `docs {symbol:"builtin:<имя>"}`.

### 8.1. Источники геометрии

| Узел | Что делает |
|---|---|
| `ico_sphere(subdiv: int, radius: f32) -> geo<mesh>` | икосфера с равномерной тесселяцией; базовая форма для органики |
| `box(size: vec3, res: int = 1) -> geo<mesh>` | параллелепипед с подразделением граней |
| `grid(size: vec2, res: vec2) -> geo<mesh>` | плоская сетка в плоскости XZ (нормали +Y); `res = (nx, nz)` — число ячеек по X и по Z раздельно (лента 2 × 24 — не 24 × 24), скаляр `res = 8` бродкастится в обе оси (v1.23). Пишет `@uv` (vec2, points): u вдоль X, v вдоль Z, 0..1 — параметрические координаты, от которых записываются формы лент/листьев/хайтфилдов (`w · (1 − uv.y²)`, `fbm(uv)`), без вычисления доли длины из `@P` |
| `mesh_line(count: int, length: f32, dir: vec3 = (0,0,1)) -> geo<points>` | ряд точек от начала координат (не центрирован); каркас для instance-цепочек; `count = 1` — одна точка в origin (детерминированный якорь), `count <= 0` — пустая геометрия (законный пустой seed для repeat-аккумулятора; v1.18 — раньше молча давал одну точку) |
| `empty_mesh() -> geo<mesh>` | пустой меш — нейтраль `merge`/`repeat` по mesh (v1.27); `mesh_line(count = 0)` остаётся пустыми **точками** |
| `empty_points() -> geo<points>` | пустое облако точек — нейтраль `merge`/`repeat` по points (v1.27) |
| `point_cloud(count: int, bounds: vec3, rng: rng) -> geo<points>` | случайное облако точек; адрес кандидата — `(point_index, xyz_lane)` |
| `import_mesh(uri: string) -> geo<mesh>` | получить immutable-меш через host `AssetProvider`; content identity внешнего ресурса входит в ключ результата |

Все источники пишут `@P`; поверхностные (`ico_sphere`, `box`, `grid`) — и `@N`. `@N` источника — **гладкая вершинная нормаль** на points (сумма нормалей инцидентных граней, нормировано): у сварного `box` углы несут диагональ своего октанта, рёбра — биссектрису, внутренние точки подразделённой стороны — точную нормаль стороны. Фасеточных point-нормалей у сварного меша не бывает по построению; для фасеток — `compute_normals(mode = flat)` (corner-`N`) либо чтение `@N` на домене faces (среднее по углам — для бокса точное направление стороны, длина < 1: `normalize(@N)`). **Правило чтения `@N` (v1.21):** на доменах corners/faces `@N` берётся из corner-колонки `N`, если она есть (после `compute_normals(mode = flat)` — фасеточная нормаль угла, на faces — точное направление грани единичной длины), иначе — из point-нормалей усреднением; на домене points — всегда point-нормали. До v1.21 corner-`N` при чтении `@N` игнорировалась — `where = dot(@N, up) > 0.9` на faces после `flat` молча не выбирал ничего.

### 8.2. Трансформации (геометрические преобразования)

| Узел | Что делает |
|---|---|
| `transform(geo, translate: vec3 = 0, rotate: vec3 = 0, scale: vec3 = 1) -> geo` | аффинный перенос/поворот (Эйлер, градусы)/масштаб всей геометрии. Атрибуты едут по **typeinfo** (§4.3): `vector` — поворот+масштаб, `normal` (в т.ч. `@N`, corner-`N`) — inverse-transpose, `point` — полная аффинная, `quaternion` (в т.ч. `@orient`) — композиция `q' = rot·q`, `none` — без изменений. У `geo<instances>` стампы `@orient`/`@scale` материализуются даже при тождественном преобразовании; `@scale` умножается на масштаб, который обязан быть равномерным — **неравномерный масштаб на `geo<instances>` невыразим стампом и даёт E611** (статически при константе, иначе в рантайме; выход — масштабировать источник или `realize` сначала) |
| `set_position(geo, offset: field<vec3> = 0, pos: field<vec3>? = none, where: field<bool> = true) -> geo` | **главный узел дисплейса**: смещение или замена `@P` per-element по полю, с маской; маска и поля — по домену points |
| `smooth(geo, iterations: int, factor: f32 = 0.5) -> geo` | лапласово сглаживание позиций; топология не меняется |
| `compute_normals(geo, mode: enum {smooth, flat, by_angle, auto} = smooth, angle: f32 = 30) -> geo` | пересчёт нормалей. `smooth` — point-`@N` (сумма нормалей граней), `by_angle` — то же с весом по углу угла грани, `flat` — corner-`N` = нормаль своей грани (фасетка), `auto` (v1.24, Blender «auto smooth») — corner-`N`: угол усредняет нормали граней вокруг своей вершины, лежащих в пределах `angle` градусов от нормали своей грани — рёбра с двугранным углом меньше `angle` гладкие, больше — жёсткие; один вызов для меша, где гнутые листы (лист, бочка, скруглённая фаска, sdf-меш) соседствуют с прямыми углами. `flat`/`auto` пишут corner-колонку и не трогают point-`@N`; чтение `@N` на corners видит corner-колонку, где она есть |
| `mirror(geo, origin: vec3 = 0, normal: vec3 = (1,0,0), weld: f32 = 0) -> geo` | к геометрии **дописывается** её отражение относительно плоскости `(origin, normal)` (Blender Mirror): позиции и `point`-колонки отражаются как точки, `vector`/`normal`-колонки (в т.ч. `@N`, corner-`N`) — как направления, обход граней переворачивается (нормали остаются наружу). Точки на расстоянии `<= weld` от плоскости **общие** для обеих половин (шов сварной; `weld = 0` ловит точно лежащие на плоскости — половина бокса из `clip` отражается в замкнутый бокс без дубликатов), остальные дублируются. Индексы: сначала исходные точки/грани, затем отражённые в том же порядке. `geo<points>` — отражение точек по тому же правилу; `geo<instances>` — E204 (кватернион `@orient` отражением в поворот не переводится — сначала `realize`); нулевая/нечисловая `normal` — E612 |

### 8.3. Топология

| Узел | Что делает |
|---|---|
| `merge<K>(a: geo<K>, b: geo<K>, ...rest: geo<K>) -> geo<K>` | конкатенация двух и более геометрий одного вида (без сварки вершин); вариадик (v1.19): `merge(a, b, c, d)` ≡ `merge(merge(merge(a, b), c), d)` бит в бит (левая свёртка, порядок точек/граней = порядок аргументов; лестницы `merge(merge(a, b), merge(c, d))` больше не нужны); минимум два операнда (E202), не-geo в хвосте — E204; разные `K` — ошибка типа. Колонки/группы объединяются по имени с нейтральным заполнением для стороны без них (по typeinfo: `quaternion` → единичный, `normal` → производные нормали, зарезервированный `tint` → белый (1, 1, 1) — множитель, нейтраль совпадает с дефолтом `realize`; остальное — нули; detail — левый операнд); **имя, присутствующее в обоих операндах, обязано жить на одном наборе доменов, а detail-значения — совпадать, иначе E609** (detail — одно значение на геометрию: merge не может представить оба, и молчаливый left-wins / zero-fill с теневанием уничтожал бы данные одной стороны) |
| `select(cond: bool, a: geo<T>, b: geo<T>) -> geo<T>` | выбор геометрии по value-bool (v1.27): константа или param компилирует только взятую ветку; иначе обе. Тернарник над `geo` — E204 с hint «select / отдельные def»; ветки одного `K` |
| `extrude(geo: geo<mesh>, distance: field<f32>, where: field<bool> = true, mode: enum {region, individual} = region, side_group: string = "", top_group: string = "") -> geo<mesh>` | выдавливание выбранных граней (маска и `distance` — поля по домену faces). `region` (Blender «extrude region»): выбранные грани уезжают одним листом вдоль **усреднённой по точке** нормали инцидентных выбранных граней (на `distance` — среднее по тем же граням), периметр выборки (рёбра с невыбранным соседом или без соседа) закрывается боковыми квадами, невыбранные грани остаются на старых точках, внутренние рёбра выборки боковых стенок не получают. `individual` — каждая грань вдоль своей нормали со своими стенками. Отрицательная `distance` — вдавливание; пустая выборка — тождество. Колонки: сдвинутые точки **копируют** исходные (points/corners), боковые грани и верх наследуют face-колонки и группы своей исходной грани (выдавленная сторона кирпича — по-прежнему кирпич), боковые квады дополнительно входят в `side_group`, верх — в `top_group`, если заданы. Замкнутый вход остаётся замкнутым; осиротевшие точки (грань уехала, соседей нет) удаляются. Не-mesh — E204 |
| `inset(geo: geo<mesh>, amount: field<f32>, depth: field<f32> = 0, where: field<bool> = true, inner_group: string = "", rim_group: string = "") -> geo<mesh>` | врезка **per-face** (Blender «inset individual»): у каждой выбранной грани появляется внутренний полигон, отступивший от рёбер на постоянную ширину `amount` (митровые смещения рёбер; отступ клампится, чтобы полигон не вывернулся) и сдвинутый вдоль нормали грани на `depth` (`> 0` — наружу, `< 0` — утоплен), кайма становится кольцом квадов. Панели, дверные полотна, оконные проёмы и фахверк — один `inset` от плоской грани бокса. Колонки: точки внутреннего полигона копируют свои исходные точки, corner-колонки внутреннего полигона и каймы **копируют** исходный угол (без интерполяции — UV/цвет угла не «плывут»), face-колонки/группы — от исходной грани; внутренний полигон дополнительно входит в `inner_group`, кайма — в `rim_group`. Не-mesh — E204 |
| `bevel(geo: geo<mesh>, width: field<f32>, where: field<bool> = true, bevel_group: string = "") -> geo<mesh>` | **фаска рёбер** (v1.24, Blender «bevel, segments = 1») сжатием граней: каждая грань получает собственные копии своих углов, отодвинутые внутрь на `width` вдоль своих скошенных рёбер (митра, где сходятся два; отступ клампится до 0.45 расстояния центроид–ребро, чтобы грань не вывернулась); зазор вдоль ребра становится квадом, зазор у вершины — n-угольником из окружающих углов (граничная вершина остаётся своей точкой как лишний угол). Скашиваются только **внутренние** рёбра — ровно с двумя гранями; граничное (одна грань: край `grid`, лист) и не-манифолдное (3+) ребро остаётся острым; `where` (faces) — ребро скашивается, когда выбраны **обе** его грани (одна выбранная грань ничего не меняет). Ничего не скошено — вход возвращается как есть (сварка сохраняется). Скругление = `bevel` + `subdivide(scheme = catmull_clark)`. Колонки: новые точки копируют исходную точку, углы — свой угол, грани фаски — среднее двух граней ребра (у вершины — от первой грани); грани фаски входят в `bevel_group` — идиома краевого износа: `set(g, "Cd", ingroup("edge") ? c * 1.4 : c, domain = faces)`, светлая кромка, по которой глаз читает объём. Сохранённый `@N`/corner-`N` **сбрасывается** (поверхность изменилась) — `compute_normals` после; `geo<instances>`/points — E204 |
| `subdivide(geo: geo<mesh>, level: int = 1, scheme: enum {catmull_clark, loop, linear} = catmull_clark) -> geo<mesh>` | подразделение поверхности, `level` итераций (`0` — тождество). `linear`: каждый k-гон → k квадов вокруг центроида через середины рёбер, форма не меняется. `catmull_clark`: та же топология с правилами Кэтмулла–Кларка (face point, edge point = среднее концов и соседних face point'ов, исходные вершины по формуле валентности; граничные рёбра/вершины — B-spline-граничные правила): бокс скругляется (углы уходят в 5/18 полуразмера), лист остаётся листом. `loop`: только треугольники (иначе E204; сначала `triangulate`) → по 4 треугольника с весами Лупа. Колонки всех доменов всегда **линейно** смешиваются топологическими весами (исходные — копия, рёберные — ½ ½, граневые — 1/k); группы — «тяжелейший» источник. Сглаживающие схемы двигают точки — стоящий `@N` схема помечает устаревшим (W006 при чтении до `compute_normals`) |
| `triangulate(geo: geo<mesh>) -> geo<mesh>` | триангуляция полигонов: квады и выпуклые n-гоны — вееры, невыпуклые — ушами; face-колонки и группы копируются на каждый треугольник, corners — от своих углов, точки не меняются |
| `merge_by_distance(geo, dist: f32) -> geo` | сварка точек ближе `dist` (union-find по равномерной сетке): кластер представляет точка с **наименьшим индексом** — её позиция, колонки и группы (без усреднения, детерминированный «first wins»); углы перенаправляются, повторяющиеся подряд углы и вырожденные грани (< 3 углов) удаляются, совпавшие грани **не** склеиваются. Чинит швы после `merge`/фрактуры/`mirror`; `geo<points>` — просто дедупликация; `geo<instances>` — E204; `dist < 0`/NaN — E204 |
| `delete(geo, where: field<bool>, domain: domain = points) -> geo` | удаление элементов по маске (инцидентные элементы старших доменов удаляются следом: точка → её грани и углы, угол → его грань, грань → её углы; младшие домены не трогаются); `detail` и не-points домен на `geo<points>`/`geo<instances>` — E204 |
| `clip(geo, origin: vec3, normal: vec3, cap_group: string = "") -> geo` | подрезка полупространством (Houdini Clip / Blender Bisect): остаётся сторона, **куда смотрит `normal`** (`dot(@P − origin, normal) >= 0`), остальное удаляется, каждая замкнутая петля разреза закрывается плоской крышкой. Грани режутся полигонально (Sutherland–Hodgman), новая точка на пересечённом ребре общая для обеих его граней — меш остаётся сварным; колонки points/corners интерполируются вдоль ребра (числа — lerp, int/bool/string — ближний конец, `@N` ренормализуется, стороне резки схема помечает `@N` устаревшим → W006 при чтении), колонки и группы faces копируются. Крышка **наследует** face-атрибуты и группы первой разрезанной грани своей петли (срез кирпича — по-прежнему кирпич) и дополнительно входит в `cap_group`, если задана; corner-колонки крышки — нули, кроме corner-`N` = `−normal`; невыпуклая крышка триангулируется ушами. Незамкнутая петля (открытая поверхность) крышки не получает. `geo<points>` — остаются точки полупространства; `geo<instances>` — E204 (сначала `realize`); нулевая/нечисловая `normal` — E612 (константа — статически). Идиома подрезки узора (черепица, кладка, ламинат): генерировать ряды **с запасом** за край, шаг подогнать под длину (`pitch = L / n`), элементы с центром за краем не класть (политика «без щепок»), остальное подрезать плоскостями края — чётный ряд кончается целым элементом, нечётный половинкой, сдвиг 1/3 даёт трети (`cottage.pgg`, def `stone_wall`) |
| `separate(geo, where: field<bool>, domain: domain = faces) -> (yes: geo, no: geo)` | расщепление на две геометрии по маске: `yes` = элементы под маской, `no` = остальное; обе стороны — каскад `delete` (маска faces оставляет все точки, маска points тянет за собой углы и грани); схема входа сохраняется у обоих выходов; `detail` и не-points домен на `geo<points>`/`geo<instances>` — E204 |
| `circle(sides: int, radius: f32 = 1) -> geo<points>` | `sides` точек по окружности в плоскости **XY** (`z = 0`, старт на +X, обход против часовой) — профиль для `sweep`; `sides < 3` — E204 |
| `bezier_points(p0, p1, p2, p3: vec3, count: int) -> geo<points>` | кубический Безье, `count` точек равномерно по параметру, пишет `@t` (f32, 0..1) — примитив авторинга пути (жилка листа, стебель, верёвка) четырьмя контрольными точками вместо подбора полиномов в `set_position`; `count < 2` — E204 |
| `resample_points(path: geo, count: int, closed: bool = false) -> geo<points>` | равномерная по длине дуги передискретизация упорядоченного пути: `count` точек от первой до последней (`closed` — по кольцу, последняя выборка не повторяет старт); point-колонки и группы пути **интерполируются** вдоль сегмента, пишется `@t` (доля длины). Делает нарисованный вручную или дрожащий путь ровным скелетом для `sweep`; `geo<instances>` / путь < 2 точек / `count < 2` — E204 |
| `sweep(path: geo, profile: geo, closed: bool = false, cap: bool = true, profile_closed: bool = true) -> geo<mesh>` | труба/балка/перила — и лента/лист (v1.23): профиль (точки в плоскости XY, порядок — `@index`; `circle()`, `mesh_line(dir = (1,0,0))`, расставленные вручную) протягивается по пути (упорядоченные по `@index` точки `geo<points>`/`geo<mesh>`: `mesh_line`, `bezier_points`, `resample_points`, любой упорядоченный набор). `profile_closed = true` — замкнутый контур (труба), `false` — открытая полилиния (полоса, желобок, V-лопасть; крышек нет, минимум 2 точки). Репер: единичные касательные центральными разностями (на концах — односторонние, при `closed` — по кольцу); **Y профиля смотрит «вверх»** (мировой +Y, спроецированный с первой касательной; для вертикального пути — +X; `@profile_scale` на вертикальном пути = `(depth, width)`: X профиля → мировой Z (глубина), Y профиля → мировой X (ширина)), X профиля = V × T, репер **параллельно переносится** вдоль пути — путь вдоль +Z отображает X профиля в мировой X, Y в мировой Y (плоская лента лежит плоско), кручение не накапливается, детерминированно. Point-атрибуты пути: `@scale` (f32, зарезервированный стамп) — равномерный масштаб профиля, `@profile_scale` (vec2) — масштаб по X (ширина) и Y (глубина) раздельно (сужение листа к кончику), `@twist` (f32, **градусы**) — поворот профиля вокруг касательной (скрутка кончика); все три потребляются и в выход не попадают. Точки кольца **наследуют остальные колонки и группы точки пути** (`@tint` на пути красит трубу) и получают `@uv` (u — поперёк профиля, v — вдоль пути, 0..1); колонки профиля игнорируются. Открытый путь с замкнутым профилем получает плоские крышки (выпуклый профиль — один полигон, иначе ушами), `cap = false` — без них; `closed = true` — тор без крышек. Квады смотрят наружу при CCW-профиле. Путь короче 2 точек, профиль короче 3 (замкнутый) / 2 (открытый), `@profile_scale` не vec2, `@twist` не f32 — E204 |
| `islands(geo: geo<mesh>) -> geo<mesh>` | разметка связных компонент; пишет `@island_id` (int, faces) |

### 8.4. SDF (первоклассный тип)

| Узел | Что делает |
|---|---|
| `sdf_sphere(r: f32) -> sdf` · `sdf_box(size: vec3) -> sdf` | аналитические примитивы |
| `sdf_union(a: sdf, b: sdf) -> sdf` · `sdf_union_smooth(a, b, k: f32) -> sdf` | объединение; smooth-вариант с радиусом скругления `k` — **всегда валидный результат**, в отличие от булевых на мешах |
| `sdf_subtract(a, b)` · `sdf_subtract_smooth(a, b, k)` · `sdf_intersect(a, b)` | вычитание/пересечение — выемки и трещины без топологического ада |
| `sdf_grind(a: sdf, b: sdf, gap: f32 = 0) -> sdf` | **притирка**: разрез `a` по срединной поверхности взаимного проникновения с `b` — `max(a, a − b + gap)`; симметричная пара `sdf_grind(a,b,g)`/`sdf_grind(b,a,g)` оставляет равномерную щель ровно `gap`, центрированную на общей контактной поверхности (`gap = 0` — тела делят одну поверхность, «притёрлись»), независимо от глубины перекрытия. Контакты ближе `gap` разводятся до `gap`; поля дальше `gap` оставляют `a` бит-в-бит неизменным. Стоимость — как у `sdf_subtract`; порядок кладки не нужен (операция симметрична, в отличие от отпечатка `sdf_subtract(a, sdf_displace(b, -g))`, который односторонен и требует цепочки) |
| `sdf_displace(s: sdf, amount: field<f32>) -> sdf` | шумовой дисплейс прямо в поле расстояний; поле вычисляется в контексте точки сэмпла (`@P` — позиция сэмпла, §4.4) |
| `sdf_instance_on_points(pts: geo<points>, source: sdf, k: f32 = 0) -> sdf` | SDF-двойник `instance_on_points`: одна immutable-форма `source` трансформируется атрибутами `@P`/`@scale`/`@orient` (кватернион; собирается `orient_from_euler`, §6.3) каждой точки и сливается в одно поле: `k = 0` — жёсткий union, `k > 0` — smooth. Per-instance стохастическая вариативность самой формы требует отдельного factory-механизма и в MVP не входит |
| `sdf_from_mesh(geo, voxel: f32) -> sdf` | вокселизация меша (для булевых над импортированной геометрией) |
| `mesh_from_sdf(s: sdf, voxel: f32, iso: f32 = 0, method: enum {marching_cubes} = marching_cubes) -> geo<mesh>` | извлечение поверхности; MVP — marching cubes с фиксированной таблицей триангуляции; surface nets — опция пост-MVP (§8.12). Решётка: шаг `voxel`, начало — conservative bbox поля минус `voxel · (1 + 0.381966)` (v1.24.2: иррациональная фаза — грань примитива в рациональной координате никогда не ложится на узлы решётки, иначе поле там равно нулю с точностью до округления и знак решает шум float → рваный лист). Следствие для авторов: фича **тоньше `voxel`** (стенка, зазор) представима только если её пересекает плоскость решётки, а это от фазы не зависит гарантированно — такая фича стабильно пропадает целиком; держи стенки ≥ 2·voxel или делай оболочку открытой (внутренний объём длиннее внешнего), а не «на 0.02 короче». Вершины, совпавшие битово (узел ровно на iso), свариваются; треугольники нулевой площади не эмитятся |

Политика границ воксельного грида: bbox выводится из bbox'ов операндов с консервативным margin'ом (учитывает `k` и заявленные амплитуды дисплейсов); доказуемая статически обрезка поля границей — ошибка валидации, иначе — предупреждение исполнителя.

**Атрибутный барьер:** `sdf` не несёт атрибутов и групп. `mesh_from_sdf` производит только `@P` (`@N` — после `compute_normals`). Перенос атрибутов/групп через SDF-участок — явным `transfer` (§8.9) или повторной разметкой после извлечения меша.

### 8.8. Распределение и инстансинг

| Узел | Что делает |
|---|---|
| `distribute_points(geo: geo<mesh>, density: field<f32>, mode: enum {poisson, uniform} = poisson, min_dist: f32 = 0, rng: rng) -> geo<points>` | разброс точек по поверхности; плотность — полем, вычисляется в позиции кандидата с барицентрической интерполяцией атрибутов поверхности; адрес кандидата включает стабильные id примитива, тайла и номер попытки; poisson выдерживает min_dist стабильным тайловым dart-throwing'ом, независимо от числа потоков; точки наследуют атрибуты поверхности, группы — по сэмплированному значению > 0.5 |
| `instance_on_points(pts: geo<points>, source: geo<mesh>, variants: geo<mesh>[] = []) -> geo<instances>` | инстансы мешей на точках; **copy-stamp**: читает с точек зарезервированные атрибуты `@scale: f32`, `@orient: vec4` (кватернион, см. `orient_from_euler` §6.3), `@variant: int`, `@tint: vec3`; логика вариативности живёт в данных, а не в узле. `variants` непуст — `@variant` выбирает источник из списка. Инстансы одного варианта делят геометрию источника; форма различается выбором заранее построенного варианта |
| `realize(inst: geo<instances>) -> geo<mesh>` | материализация инстансов; единственное место, где они «дорожают». Переносит **все домены** источника: атрибуты и группы points/corners/faces (union-схема по вариантам с нейтральным заполнителем по typeinfo; имя, общее для нескольких вариантов, обязано жить на одном наборе доменов с одним typeinfo — иначе **E609**, правило merge: realize и есть слияние штампованных копий), `@variant` вне `[0, variants)` — **E611** (не clamp), тегированные колонки трансформируются стампом `T(P)·R(orient)·S(scale)` по своему typeinfo (§4.3; `@N`/corner-`N` как normal, vector-атрибуты поворачиваются, point-атрибуты переезжают к якорю); detail — от первого варианта (правило merge); `@tint` материализуется на points |

### 8.9. Сэмплинг между геометриями

| Узел | Что делает |
|---|---|
| `raycast(target: geo<mesh>, origin: field<vec3>, dir: field<vec3>) -> (hit: field<bool>, pos: field<vec3>, n: field<vec3>, dist: field<f32>)` | постановка объектов на поверхность, слепки нормалей |
| `transfer(geo, source: geo, attrs: string[], mode: enum {nearest} = nearest) -> geo` | перенос именованных атрибутов между геометриями (террейн → камни: wetness, biome) |
| `bake_ao(geo: geo<mesh>, rays: int = 32, distance: f32 = 0, rng: rng, domain: enum {auto, points, corners} = auto, name: string = "ao") -> geo<mesh>` | **запечь ambient occlusion** (v1.24) в f32-атрибут `@ao` ∈ [0, 1] (1 — открыто, 0 — полностью закрыто): из каждого элемента `domain` — `rays` лучей по косинусно-взвешенной полусфере вокруг его нормали (стратифицированный джиттер от `rng` — детерминированно), попадание на расстоянии `t < distance` затемняет на `1 − (t/distance)²`; `distance = 0` → четверть диагонали bbox. Нормали: `corners` — corner-`N` (`compute_normals(flat/auto)`), `points` — `@N` или производные; `auto` — corners, если corner-`N` есть, иначе points. **Одностороннее**: попадания в грань с изнанки не считаются (луч из сварной выпуклой вершины со средней нормалью уходит внутрь собственного бокса — иначе каждый угол бокса был бы чёрным) — открытый лист/`grid` затеняет только со своей лицевой стороны, закрытый объём (box, sdf-меш) — всегда; для «крышки» над чем-то бери тонкий box, не `grid`. Печётся **по элементам**: большой плоский квад несёт AO только в четырёх вершинах — крупные плоскости сначала `subdivide(scheme = linear)`. Читатели: PggViewer и `PggTool run --obj` умножают `@Cd` (или нейтральный серый) на `@ao`; в OBJ отдельного канала AO нет. `geo<instances>`/points — E204 |

### 8.10. Агрегаторы (мост поле → значение)

| Узел | Что делает |
|---|---|
| `bbox(geo) -> (min: vec3, max: vec3)` · `extent(geo) -> vec3` · `centroid(geo) -> vec3` | геометрические сводки |
| `count(geo, domain: domain = points, where: field<bool> = true) -> int` | число элементов (под маской) |
| `min_of / max_of / avg_of / sum_of(field, on: geo, where: field<bool> = true) -> f32` | редукции полей; порядок суммирования — строго по `@index` (детерминизм) |
| `value(field, on: geo, where: field<bool> = true) -> T` | значение поля на **ровно одной** точке `on` под маской, в собственном типе поля `T` (числовые и векторные типы; тип известен статически, если `on` с закрытой схемой несёт колонку, иначе провизорный f32 → runtime-тип по значению). 0 или 2+ выбранных точек — **E601**. Аксессор модели строк в `foreach` по точкам (§5.4): `value(@n, on = row)`, `value(@P, on = row)`. Все агрегаторы — **значения** внутри объемлющего поля: `set_position(g, offset = @P * value(@k, on = pts))` и передача `value(...)` аргументом def'а, чей параметр стоит в поле, читают `@k` на `on`, а не на геометрии, где потребляется поле (статическая проверка E302 это учитывает) |

### 8.11. Фрактура (с foreach)

| Узел | Что делает |
|---|---|
| `fracture(geo: geo<mesh>, planes: geo<points>, rng: rng) -> geo<mesh>` | воронои-разбиение по точкам; стохастические решения адресуются стабильным индексом входной плоскости и локальным номером попытки; результат — куски с `@island_id`, готовый вход для `foreach` |

**Заметка реализации:** fracture — это булеаны «меш × набор плоскостей»; реализация обязана явно определить численную модель, обработку касательных контактов, требования к входному мешу и поведение при неразрешимой конфигурации. Конкретная библиотека точных предикатов не является частью семантики языка.

**Численная модель v0 — SDF-Вороной** (реализована в E7; точные mesh-булеаны — пост-MVP): сайты дедуплицируются точным совпадением (keep-first); 0 сайтов или пустой меш — ошибка **E608**; 1 сайт — входной меш с `@island_id = 0` без разреза. Вход вокселизуется один раз с авто-вокселем `maxExtent/128` (страж E306); для сайта i поле ячейки — аналитическая полусечение `max over j≠i of dot(p − (pi+pj)/2, normalize(pj−pi))`, кусок = marching cubes из пересечения с полем меша (watertight, кэп-грани — плоскости разреза); пустой кусок (сайт вне меша) пропускается. Куски мержатся жёстко в порядке сайтов с плотным `@island_id` (faces). Стохастических решений в модели нет: равноудалённость (ties) разрешается порядком сайтов, обязательный параметр `rng` зарезервирован под будущие модели и в v0 не читается. Требование к входу — замкнутый меш (знак поля — псевдо-знак по ближайшему треугольнику, как у `sdf_from_mesh`, §8.4).

### 8.12. Пост-MVP (запланировано, в MVP не входит)

кривые как домен (`curve_line`, `curve_to_mesh`, `resample_curve` — в MVP путь = упорядоченные точки + `sweep`, §8.3), `bevel` с `segments > 1` (скругление сейчас — `bevel` + `subdivide`), `remesh`, `uv_unwrap`, кривизна, simulation zone (feedback по кадрам анимации), erosion-симуляция как встроенный узел (в MVP — через `repeat` + поля), surface nets как второй `method` у `mesh_from_sdf`, GPU-backend полей (§12.5), factory-механизм per-instance вариативности SDF-формы (§8.4).

## 9. Подсистема отладки

Принцип: **диагностика — это тоже узлы**. Раз связь = имя, снять данные между узлами = применить инспектор к имени. Инспекторы — чистые, ленивые, не влияют на семантический слой.

### 9.1. Уровни детализации вывода

Сырые данные (10⁵ вершин) не нужны ни человеку, ни LLM (сожжённый контекст). Иерархия от дешёвого к дорогому:

| Уровень | Инспектор | Вывод | Кому |
|---|---|---|---|
| **L0** | `schema(geo)` | подпись геометрии: `mesh: 5122 pts, 10240 tri; attrs: N(vec3,pts), slope(f32,pts), wetness(f32,detail); groups: cliff_faces, flat_tops` | оба; отвечает на половину вопросов «почему узел ругается» |
| **L1** | `stats(geo, field)` · `coverage(mask, on: geo)` | числа: `slope: mean 0.41, p50 0.38, p90 0.78, min 0.02, max 0.99`; `mask true: 18.2% (934/5122)` | **основной формат для LLM**: по `coverage = 0%` она сама видит пустую маску |
| **L2** | `table(geo, cols = [@P, @scale], limit = 8, order = @index)` | сэмпл строк, детерминированно отсортированный | оба |
| **L3** | `preview(geo, view = iso, res = 512)` | рендер-картинка; опционально ASCII-отрисовка высот/масок для текстового потребления | человек (+LLM через ASCII) |

### 9.2. Свойства

- **Ленивая частичная прогонка.** Запрошен `stats(rock)` — вычисляется граф ровно до `rock`, всё ниже по потоку не трогается. Итерационный цикл LLM: правка → пробник → ответ за миллисекунды.
- **Детерминизм пробников.** Имя диагностики = (имя ребра, тип инспектора, параметры). Стабильно между запусками ⇒ ответы можно диффать, LLM рассуждает «было — стало».
- **Срезание слоя.** Флаг runtime `debug=off` удаляет все инспекторы из плана; продакшен-кэш при этом не инвалидируется (отладочный кэш отдельный).

### 9.3. `tap` — постоянные метки наблюдения

```text
tap rock            # всегда снимать schema+stats по умолчанию
tap stats: rock.flat_tops
```

`tap` в файле — «здесь смотрим всегда»; срабатывает при прогоне в debug-режиме. Последний компонент пути может адресовать группу или атрибут на геометрии (`rock.flat_tops`).

### 9.4. Пробники по instance path

- CLI: `engine run rock.pgg --probe "world.cliff_wall[0].make_rock[3]:stats"` — доступ без правки файла.
- Инспектор внутри def срабатывает **на каждом экземпляре**: 50 камней — 50 срабатываний. Режим агрегации `aggregate = stats`: одна строка `disp: mean 0.31 ± 0.04 по 50 экземплярам` — идеальный формат для LLM.

### 9.5. Стеки ошибок через границы

Ошибка внутри def показывает цепочку вызовов:

```text
E302 в fbm_displace, строка 3: атрибут @N отсутствует
  ← вызвано из make_rock, строка 7 (аргумент geo = m)
  ← вызвано из cliff_wall, строка 12
```

LLM по стеку различает, чей контракт нарушен — её или библиотечный.

### 9.6. Пробники полей, срезов и здоровья меша (`sample` / `slice` / `check` / `lattice` / `table[where]` / `find` / `bbox` / `gap`)

Три инспектора для вопросов «какое значение поле принимает в этой точке» и «насколько меш здоров» — то, ради чего раньше переписывали SDF на стороне (инцидент `mc_thin_shell_slivers.md`: тонкая стенка оболочки и вырожденные треугольники диагностируются одной командой). Это CLI/API-пробники (`--probe`, RPC `probe`); в `tap` они не включаются.

**Грамматика параметров** (общая для `[...]` любого инспектора): пары `name=value` разделяются запятыми **верхнего уровня** — запятые внутри скобок не разделители; векторные значения пишутся в скобках `(x,y,z)`; список точек — несколько векторов через `;` внутри одного значения: `at=(0,1,3.4);(1,0,0)`. Множество допустимых имён зависит от инспектора, неизвестное имя — E606. `limit` (только `table` и `check`) и `aggregate=stats` (только `schema`/`stats`/`coverage` и дефолтная пара) — типизированные параметры; остальные хранятся сырыми и разбираются инспектором.

**`bbox` / `gap` (v1.27)** — измерения геометрии без кадра:

```text
house:bbox                              # min/max/center/size всего geo
house:bbox[group=stone]                 # то же по точкам группы (пустая — E606)
house:gap[a=group:stone, b=group:brick, axis=x]  # зазор bbox по оси; перекрытие отрицательное
```

`a`/`b` — `group:<name>` или голое имя группы на том же geo. MCP-сахар: `pgg_measure(node, a, b, axis)`.

**`sample`** — значение поля/расстояния в точках:

```text
shell:sample[at=(0,1,3.425);(1,0,0)]        # точки через `;`
shell:sample[from=(2,0,0),to=(4,0,0),n=41]  # профиль: n строк от from до to включительно (n >= 2, дефолт 41)
```

- Таргет `sdf`: значение — знаковое поле.
- Таргет `geo<mesh>`: псевдо-знаковое расстояние — ближайшая точка на меше (BVH), знак по нормали ближайшего треугольника (тот же оракул, что у `sdf_from_mesh`); заголовок записи несёт пометку ` (pseudo-sign distance from mesh)`.
- Таргет `geo<points>`: беззнаковое расстояние до ближайшей точки, пометка ` (unsigned distance from points)`.

Заголовок — нормализованное эхо параметров (`sample[at=(2, 0, 0);(0, 0, 0)]`), далее строки `x y z value`, float `%g`.

**`slice`** — срез поля плоскостью:

```text
shell:slice[axis=z,at=3.425,step=0.25]                     # ASCII-карта
shell:slice[axis=z,at=3.425,step=0.25,format=csv,iso=0.0]  # значения
shell:slice[axis=z,at=3.425,step=0.25,bounds=(-3,0,3,3.5)] # явные границы в плоскости среза
```

- Плоскость перпендикулярна `axis` на координате `at`; координаты плоскости (u,v): `axis=x` → (y,z), `axis=y` → (x,z), `axis=z` → (x,y). `bounds=(u0,v0,u1,v1)`; по умолчанию — проекция conservative bbox таргета на плоскость.
- Узлы решётки: `u0 + i·step`, `v0 + j·step`; размеры `round((u1-u0)/step)+1 × round((v1-v0)/step)+1`. Ширина ASCII ограничена **120 колонками**: при превышении шаг увеличивается, в заголовке пометка `step widened to … (120 col cap)`.
- Значения — те же, что у `sample` (sdf-поле / псевдо-знак расстояния до меша / расстояние до точек), с той же пометкой в заголовке.
- `format=ascii` (дефолт): `#` где `value <= iso`, `.` где `> iso`; первая строка — верх карты (`v = v1`). `format=csv`: строки `i,j,value` (`%g`) в порядке хранения (j по возрастанию, внутри — i).
- Заголовок: `slice[<нормализованные параметры>] (W x H, bounds (u0, v0)..(u1, v1)[, пометки])`.

**`check`** — здоровье меша (только `geo<mesh>`; `limit` ограничивает списки индексов, дефолт 8):

```text
house:check
house:check[warn_aspect=10,limit=16]
```

Строки `key value` в фиксированном порядке:

| Ключ | Смысл |
|---|---|
| `degenerate N` | грани с нулевой площадью (Newell), повторным индексом точки, выходом индекса за диапазон или < 3 углов; при N>0 — строка `degenerate_faces` с первыми `limit` индексами |
| `nonmanifold N` | неориентированные рёбра с инцидентностью > 2 |
| `boundary N` | рёбра с инцидентностью 1 (**информативно**: норма для открытых мешей, в `issues` не считается) |
| `isolated N` | точки, не входящие ни в одну грань |
| `nan N` | точки с NaN/inf компонентой в `@P`/`@N`/`@Cd` |
| `components N` | компоненты связности граней через общие точки (**информативно**: N>1 — норма для fracture/мержей) |
| `oriented_mismatch N` | компоненты, где направленное ребро (a,b) встречается 2+ раза (у согласованно ориентированного закрытого меша каждое ребро проходится по разу в каждую сторону) |
| `edge_min X` · `edge_median X` | минимум и медиана (nearest-rank) длин сторон граней, `%g`; `-` при отсутствии рёбер |
| `needles N` | грани с aspect > `warn_aspect`: отношение длиннейшего ребра к минимальной высоте треугольника = `longest²/(2·area)`, максимум по fan-триангуляции грани; при N>0 — `needle_ratio P%` и `needles_faces` |
| `ok` / `issues N` | итог: N = degenerate + nonmanifold + isolated + nan + oriented_mismatch + needles |

Вырожденные грани не вносят вклада в рёберную и ориентационную статистику (их обход бессмыслен), но их точки не считаются изолированными и участвуют в связности.

**`lattice`** — решётка `mesh_from_sdf` глазами автора (только `sdf`-таргет; на `geo` — E606 «lattice needs an sdf value»):

```text
shell:lattice[voxel=0.05]
```

Печатает ту решётку, которую `mesh_from_sdf(s, voxel)` реально сэмплирует (общая формула с экстрактором, `meshFromSdfLattice`): заголовок `lattice[voxel=<v>] (dims Dx Dy Dz, origin (x, y, z), step <v>)` — origin = conservative bbox − voxel·(1+фаза) (фаза — сопряжённое золотое сечение, §8.4), dims = ceil(span/voxel)+1; превышение оси — пометка `axis overflow (>4096 voxels, E306)` в заголовке, пустое поле — `(empty conservative bbox)`. Далее предупреждения обходом DAG (детерминированный порядок: сначала плоскости, затем центры сфер, затем пары; внутри — сортировка по оси/координате, ничьи — в порядке первого появления; дубликаты строк схлопываются):

- `warn: face plane x=<v> is <d> from lattice plane (threshold <t>)` — осевая плоскость грани `sdf_box`-примитива ближе `0.05·voxel` к плоскости решётки (нулевое поле ровно на узле — источник бахромы MC, инцидент `mc_thin_shell_slivers.md`);
- `warn: sphere center x=<v> is <d> from lattice plane (threshold <t>)` — то же для координаты центра `sdf_sphere`;
- `warn: parallel faces x=<a> and x=<b> are <d> apart (< 2*voxel)` — пара параллельных плоскостей РАЗНЫХ примитивов ближе 2 вокселей (стенка, которую MC не представит; совпадающие плоскости печатают `d = 0`).

Якоря `sdf_instance_on_points` разворачиваются через трансформ, когда поворот — осевой (перенос + uniform scale + знаковая перестановка осей, в т.ч. повороты на 90°); остальные якоря пропускаются со строкой `note: K instance anchor(s) skipped (non-axis-aligned rotation)` после заголовка. `Grid` (sdf_from_mesh) и `VoronoiCell` аналитических осевых плоскостей не имеют и не анализируются. Последняя строка — `warns N` (всегда, в т.ч. `warns 0`).

**`table[where=<expr>,limit=N]`** — строки `table` только по точкам, где предикат истинен. Предикат — обычное выражение PGG над points-доменом таргета (`@name`, `@P`, `@index`, арифметика, сравнения, `&` `|` `!`, тернарник, функции §6.3; swizzle `.x` в грамматике нет — компоненты через `dot(@N, (0, 1, 0))`; идентификаторы разрешаются в binding'и файла). Заголовок `table[where=<expr>,limit=L] (first K of M matching, N total)`; строки сохраняют реальный `@index` точки. Предикат обязан вычисляться в bool-поле: не-bool поле/константа — E606 с подсказкой про сравнение; отсутствующий атрибут — E302 от вычисления предиката. Предикат на не-geo таргете — E606. Константный предикат (`where=1 < 2`) валиден и вещается на все/ноль точек.

**`find[where=<expr>]`** — быстрый ответ «сколько и где» (без `where` — E606):

```text
house:find[where=@ao < 0.9]
find[where=@ao < 0.9]
count 123 of 5122
bbox (-1.5, 0, -2)..(1.5, 3.4, 2)
groups: stone (100), tile (23)
```

`count K of N` — сколько точек прошло предикат из всего; `bbox` — bounding box подмножества (при K=0 опускается); `groups: g (K)` — **points-группы**, в которые входит K>0 выбранных точек (имена отсортированы; строка опускается, когда таких групп нет). `limit`/`aggregate` к `find` не применяются.

## 10. Текст ↔ нодовая проекция

- Проекция — **рендер графа, выведенного из имён**; отдельного формата хранения не существует. Имя = нода; использование имени = входной пин.
- **Раскладка — опциональные подсказки в комментариях**, не часть семантики:
  ```text
  rock = set_position(base, offset = @N * n * 0.35)  # @pos 340 120
  ```
  IDE дописывает координаты при ручном перетаскивании; LLM генерирует без них → auto-layout; подсказка удалена/грязна → ничего не ломается. Запрещено делать раскладку частью семантики (иначе машинные правки разрушают вид).
- def в проекции — нода с возможностью провалиться внутрь; путь проваливания = instance path (§7.7). Зоны repeat/foreach — подграфы с портами «вход итерации»/«выход итерации» и петлёй состояния (§5.4). Текст, отладка и визуализация говорят одними адресами.
- Проекция MVP: чтение + навигация + просмотр пробников. Редактирование мышью с записью в текст — отдельный этап.

**Заметка реализации (E8, v1.6):** проекция реализована приложением **PggViewer** (`src/apps/PggViewer`, sibling PggTool'а) поверх библиотечных модулей `src/libs/pgg/src/graph.h/.cpp` (вывод графа из AST) и `layout.h/.cpp` (авто-раскладка + подсказки). Вывод: binding → нода (op — внешний вызов, иначе `expr`; цели → out-пины, мультивыход — несколько пинов); каждое чтение имени → провод (входной пин — имя named-аргумента, позиционный — отдельный безымянный); bare ident в named-arg позиции → провод, только если имя определено (зеркало правила enum-литералов валидатора — фантомных проводов от `mode = poisson` нет); `param`/`output`/`import`/`tap` — чипы, expect/ensure — не ноды. Зоны — рамки с синтетическими портами «вход итерации»/«выход итерации» и петлёй состояния: чтение state до единственного связывания — от входного порта, после — от binding'а (scope-механика валидатора). def-вызов — свернутая нода с проваливанием; instance-нумерация совпадает с экспансией бит-в-бит (k-й вызов def'а в порядке экспансии = `foo[k]`; счётчики глобальны, поэтому граф строится одним общим обходом, а не per-def) и кросс-проверяется тестами против `FlatProgram::instances`. Формат подсказки запинен: `@pos X Y` (целые, любой знак; центр ноды) в любом месте trailing-комментария строки binding'а, первое совпадение — подсказка; грязная/обрезанная (`@pos abc`, `@pos 1`, `@position 1 2`) молча игнорируется. Write-back (`applyPosHint`): совпадение есть → заменяются только координаты; нет → дописывается `  # @pos X Y` в конец строки (после существующего trailing-комментария); re-parse после write-back даёт тот же AST (`astEqual`), форматтер подсказки сохраняет. Авто-layout — детерминированный Sugiyama-lite (слои по longest path без петлевых рёбер, barycenter-сметы, ничьи по спану); подсказка побеждает раскладку (локальные пересечения допустимы). Скоуп MVP зафиксирован: чтение + навигация (пан/зум/drag с write-back подсказки, проваливание с breadcrumb) + просмотр пробников (синхронный прогон через `RunParams::probes`; параметры файла вводятся в панели). Write-back ограничен главным файлом (тела def из модулей — read-only).

## 12. Требования к runtime

1. **Иммутабельная геометрия + structural sharing:** узел копирует только изменённые таблицы атрибутов/топологию.
2. **Memoization полей** по ключу (поле, контекст геометрии) — устранение повторных вычислений FBM в множественных потребителях.
3. **Пулы памяти для полей:** буферы per-element переиспользуются внутри узла; аллокации в горячем цикле запрещены.
4. **Параллелизм:** per-element evaluation полей и `foreach` по кускам — в пуле потоков; внутри одного numeric profile результат не зависит от числа потоков (N1). Воспроизводимые агрегации используют фиксированный порядок обхода.
5. **GPU-backend (пост-MVP):** компиляция подграфов полей в compute-шейдеры; архитектура полей (чистые функции от элемента) выбрана в т.ч. под это — не закрывать путь решениями, требующими CPU-контекста в теле поля. CPU и GPU — разные numeric profiles, бит-в-бит равенство между ними не гарантируется; backend/profile входят в ключ кэша и отчёт запуска.
6. **Кэш:** in-memory LRU обязателен; persistent-кэш на диске — опциональный слой с тем же ключом.
7. **Лимиты:** конфигурируемый потолок элементов на realize (защита от случайного взрыва геометрии, ошибка E602 с подсказкой).
8. **Выходы и экспорт:** runtime возвращает все допустимые типы `output` (§6.7) в собственной модели. Сериализация `geo<K>`, `sdf` и скалярных значений, а также преобразование в host-форматы — отдельные адаптеры и отдельный контракт.

## 13. Формальная грамматика (ядро, EBNF)

Лексика (эскиз): комментарии — `#` до конца строки; операторы разделяются `NEWLINE`; отступы семантики не несут — блоки только фигурными скобками, пробельное оформление приводится форматтером (§6.4); числа — целые и с плавающей точкой (точка, экспонента); строки — двойные кавычки, escapes `\\` `\"` `\n`; `TRIPLE_STRING` — `"""..."""`; идентификаторы — `[A-Za-z_][A-Za-z0-9_]*`. Зарезервированные ключевые слова: `def expect ensure tap import as repeat foreach in param output none true false`.

```ebnf
file         = { import_stmt | param_stmt | def_stmt | stmt | output_stmt } ;

import_stmt  = "import" qualified_name [ "as" ident ] [ "@" version ] NEWLINE ;
param_stmt   = "param" ident ":" type [ "=" literal ] NEWLINE ;
output_stmt  = "output" ident NEWLINE ;

def_stmt     = "def" ident "(" [ params ] ")" "->" "(" outputs ")" "{" NEWLINE
               docstring { expect_stmt } { stmt } { ensure_stmt } "}" NEWLINE ;
params       = param { "," param } ;
param        = ident ":" type [ "=" literal ] ;
outputs      = out_decl { "," out_decl } ;
out_decl     = ident ":" type ;
docstring    = TRIPLE_STRING ;
expect_stmt  = "expect" ( ident "has" attr_ref | aexpr ) [ ":" string ] NEWLINE ;
ensure_stmt  = "ensure" ( ident "has" attr_ref | aexpr ) [ ":" string ] NEWLINE ;

stmt         = binding NEWLINE
             | tap_stmt NEWLINE
             | repeat_zone
             | foreach_zone ;
binding      = targets "=" aexpr ;
targets      = ident { "," ident } ;                     (* 1..n: деструктуризация *)
tap_stmt     = "tap" [ ident ":" ] path NEWLINE ;

repeat_zone  = targets "=" "repeat" "(" aexpr "," "iterations" "=" aexpr ")"
               "|" ident { "," ident } "|" "{" NEWLINE
               { stmt } "}" NEWLINE ;
foreach_zone = ident "=" "foreach" ident "in" aexpr "{" NEWLINE
               { stmt } "}" NEWLINE ;

aexpr        = ternary ;
ternary      = or_expr [ "?" aexpr ":" aexpr ] ;         (* cond ? a : b *)
or_expr      = and_expr { "|" and_expr } ;
and_expr     = cmp_expr { "&" cmp_expr } ;
cmp_expr     = add_expr [ cmp_op add_expr ] ;            (* без цепочек a > b > c *)
add_expr     = mul_expr { ("+" | "-") mul_expr } ;
mul_expr     = unary { ("*" | "/" | "%") unary } ;
unary        = [ "-" | "!" ] unary | postfix ;
postfix      = primary | call ;                          (* вызовы допустимы внутри выражений *)
primary      = literal | ident | attr_ref | "(" aexpr ")" ;
attr_ref     = "@" ident ;                               (* @P, @N, @index, @slope *)
call         = qualified_name "(" [ args ] ")" ;
args         = arg { "," arg } ;
arg          = [ ident "=" ] aexpr ;

type         = "geo" [ "<" geo_kind ">" ] | "sdf" | "rng"
             | "f32" | "int" | "bool"
             | "vec2" | "vec3" | "vec4" | "string"
             | "field" "<" type ">"
             | "domain"
             | "enum" "{" ident { "," ident } "}"
             | type "?"                                 (* optional, значение none *)
             | type "[" "]" ;                           (* список, напр. string[] *)
literal      = number | string | bool | vec_literal | ident | "none" ;
vec_literal  = "(" signed_number "," { signed_number "," } signed_number ")" ;
                                        (* константы со знаком; ≥2 компоненты,
                                           иначе это скаляр в скобках; см. vec3() *)
version      = number "." number ;
path         = ident { "." ident | "[" number "]" } ;
qualified_name = ident { "." ident } ;
geo_kind     = "mesh" | "points" | "curve" | "instances" ;
domain_lit   = "points" | "corners" | "faces" | "edges" | "detail" ;
```

`ident` в позиции `literal` — литерал enum или домена (различается по объявленному типу параметра). Дефолты параметров — только константы, не ссылки на другие имена (§6.6).

Приоритет: `&` и `|` связывают **слабее** сравнений (`@slope > 0.4 & @h > 0.3` читается как `(@slope > 0.4) & (@h > 0.3)`) — осознанное отклонение от Python в сторону GLSL: маски комбинируются без скобок.

Семантические ограничения поверх грамматики (проверяет валидатор): SSA (§6.2.1; выходной порт каждого канала состояния зоны связывается ровно один раз, §5.4), define-before-use (§6.2.2), выходы def определены в теле ровно один раз (§7.1), rng-дисциплина (§7.3), DAG вызовов def (§7.6), DAG импортов, разрешение qualified names, наличие корней исполняемого файла (§6.7), типовая совместимость полей (E205), принадлежность enum-значений (E206), привязка param (E604), контракты expect/ensure при статически выводимой схеме.

### 13.1. Реализация парсера: ANTLR4 (решение)

Парсер реализуется на **ANTLR4** (C++ target): единая грамматика `Pgg.g4`, AST собирается грамматическим композитором через однострочные actions в правилах (§13.2). Рассматривались ручной recursive descent и bison/flex; выбран генератор по двум аргументам:

- **wasm-поставка не содержит парсера.** Под Emscripten собирается только просмотрщик/игровой рантайм с запечённой геометрией; парсинг — инструмент авторинга и живёт на desktop-платформах, поэтому вес и ограничения C++-рантайма ANTLR (ATN) для wasm-цели несущественны.
- **Генератор не обязателен на машине сборки.** Сгенерированные lexer/parser-файлы коммитятся в репозиторий как артефакты (генерация с `-no-listener -no-visitor`, §13.2); Java-инструмент ANTLR нужен только при правке `Pgg.g4`.

Обязательства решения:

1. **Версии инструмента и рантайма пинуются вместе** (jar == версии vcpkg-порта `antlr4`); перегенерация — только закоммиченным скриптом.
2. **Артефакты не редактируются руками и не протухают:** CI-проверка «перегенерировать → diff пуст».
3. **Диагностика — свой error listener:** синтаксические ошибки отображаются в коды E1xx со спанами (§11); дефолтные сообщения ANTLR («mismatched input …») в пользовательский вывод не попадают — текст ошибок часть LLM-интерфейса языка.
4. **Комментарии и trivia — на hidden channel:** форматтер (§6.4) сохраняет `#`-комментарии при канонической перезаписи.
5. Грамматика §13 переносится в `.g4` почти механически: NEWLINE — явный токен (не skip), `TRIPLE_STRING` — нежадное лексер-правило; зоны однозначны по ключевому слову после `=` (`repeat`/`foreach` зарезервированы и вызовами в выражениях быть не могут, поэтому `|state|` после `repeat(...)` не конфликтует с бинарным `|`).

### 13.2. Сборка AST: грамматический композитор (gc)

Синтаксис держится минимальным: правила `.g4` не содержат логики, только триггеры — однострочные вызовы **грамматического композитора** (`gc`). Фабрика узлов, спаны, накопление составных конструкций и переживание неполного ввода живут в `gc` (обычный C++20, тестируется без парсера). Данные идут двумя каналами:

- **Семантические значения правил** (`returns` + метки элементов) — канал по умолчанию для конструкций с фиксированной арностью: литералы, операторы, вызовы, конструкторы. Аналог `$$ = gc.newAdd($1, $3)` из bison, метки вместо позиций:

  ```antlr
  expr : l=expr '+' r=expr { $result = gc.newAdd($l.result, $r.result, ctx); } # Add
  ```

  В ANTLR операторы — альтернативы одного леворекурсивного правила с метками `#`, а не отдельные правила вида `plus_operator`; триггер на альтернативу — тот же приём.
- **Кадры накопления в `gc`** — для составных конструкций с открытым телом: `def` (docstring/expect/тело/ensure), зоны, файл. Скобочная пара mid-rule actions: после заголовка `gc.beginDef(...)` — дальше `gc` накапливает детей на своём стеке — в конце `$result = gc.endDef(ctx)`: `endX` склеивает узел и возвращает его тем же семантическим значением, так что для родителя оба канала неразличимы.

Критерий выбора канала: фиксированная арность → семантические значения; открытое тело или секции → кадр `gc`.

Обязательства схемы:

1. **В action — ровно один вызов `gc`** (плюс передача `$x.result`/`ctx`). Ветвления, циклы и сборка списков в грамматике запрещены — это код `gc`.
2. **Контракт небаланса:** при error recovery ANTLR может не выполнить `endX` для начатого кадра; `gc` обязан переживать незакрытые кадры (отброс на синхронизации/`endFile`) и превращать error-лексемы в error-сентинелы — частичный AST нужен линту «все проблемы за один прогон» (E0). Симметричный контракт входов (v1.7): все pointer-valued `returns` инициализируются `= nullptr` в самой грамматике (error-recovery завершает правило, не выполнив action, — semantic value на этом пути гарантированно nullptr, а не мусор), а `gc` превращает nullptr в error-сентинелы (`ErrorExpr`) на входе каждой фабрики.
3. **Валидации в `gc` нет** — он только склеивает структуру; семантические коды (§13) проверяет отдельный проход валидатора по готовому AST.
4. **Listener/visitor не генерируются** (`-no-listener -no-visitor`): сборка идёт через actions. Цена гибрида — `.g4` привязана к C++-actions; принимается осознанно: артефакты коммитятся (§13.1), вторая целевая платформа грамматики не планируется.

## 16. Приложение A: сквозной пример (башня композиции)

```text
param world_seed: int

# --- уровень 1: примитивная обёртка ---
def fbm_displace(geo: geo, scale: f32 = 2.5, amp: f32 = 0.35, rng: rng) -> (out: geo) {
    """Дисплейс слоистым шумом вдоль нормалей.
    Требует: @N на точках. Пишет: @disp (f32, точки).
    """
    n         = fbm(scale = scale, octaves = 5, rng = rng)
    displaced = set_position(geo, offset = @N * n * amp)
    out       = set(displaced, "disp", n * amp)
}

# --- уровень 2a: SDF-ядро валуна (для плавного сливания) ---
def make_rock_sdf(size: f32 = 2.0, roughness: f32 = 1.0, rng: rng) -> (out: sdf) {
    """SDF-ядро валуна — вход для sdf_instance_on_points и mesh_from_sdf."""
    expect size > 0: "размер в метрах, положительный"
    ball = sdf_sphere(r = size)
    out  = sdf_displace(ball, fbm(@P * 1.5, octaves = 5, rng = rng) * 0.3 * roughness)
}

# --- уровень 2b: одиночный валун-меш ---
def make_rock(size: f32 = 2.0, roughness: f32 = 1.0, rng: rng) -> (out: geo<mesh>) {
    """Один валун: SDF-ядро + шумовой дисплейс + атрибуты крутизны.
    Пишет: @slope (f32, точки), группы cliff_faces / flat_tops.
    """
    expect size > 0: "размер в метрах, положительный"
    shape_rng  = split_rng(rng, key = "shape")
    tops_rng   = split_rng(rng, key = "tops")
    detail_rng = split_rng(rng, key = "detail")
    src     = make_rock_sdf(size = size, roughness = roughness, rng = shape_rng)
    raw     = mesh_from_sdf(src, voxel = size * 0.02)
    shaped  = compute_normals(raw)
    sloped  = set(shaped, "slope", 1 - dot(@N, (0, 0, 1)))
    cliffed = mark(sloped, "cliff_faces", where = @slope > 0.6)
    topped  = mark(cliffed, "flat_tops", where = (@slope < 0.15) & (fbm(scale = 6, rng = tops_rng) > 0.5))
    out     = fbm_displace(topped, scale = 3.0, amp = 0.1 * roughness, rng = detail_rng)
}

# --- уровень 3: составная структура ---
def cliff_wall(length: f32 = 120, rng: rng) -> (wall: geo<mesh>, anchors: geo<points>) {
    """Стена из валунов вдоль линии: SDF-инстансы одной формы сливаются в одно поле,
    повторяемость маскируют @scale и @orient на точках. anchors — точки посадки деталей."""
    scale_rng   = split_rng(rng, key = "scale")
    orient_rng  = split_rng(rng, key = "orient")
    source_rng  = split_rng(rng, key = "source")
    tops_rng    = split_rng(rng, key = "tops")
    scatter_rng = split_rng(rng, key = "scatter")
    line0    = mesh_line(count = int(length / 7.5), length = length)
    line1    = set(line0, "scale", random(lo = 0.7, hi = 1.4, rng = scale_rng))
    line     = set(line1, "orient", orient_from_euler(random_vec(lo = (0, 0, 0), hi = (0, 360, 0), rng = orient_rng)))
    rock_src = make_rock_sdf(size = 3.0, rng = source_rng)
    wall_sdf = sdf_instance_on_points(line, source = rock_src, k = 0.8)
    raw      = mesh_from_sdf(wall_sdf, voxel = 0.1)
    shaped   = compute_normals(raw)
    sloped   = set(shaped, "slope", 1 - dot(@N, (0, 0, 1)))
    wall     = mark(sloped, "flat_tops", where = (@slope < 0.15) & (fbm(scale = 6, rng = tops_rng) > 0.5))
    anchors  = distribute_points(wall, density = ingroup("flat_tops") * 3, mode = poisson, min_dist = 0.4, rng = scatter_rng)
}

# --- уровень 4: мир ---
world_rng = rng_from_seed(world_seed)
wall_rng  = split_rng(world_rng, key = "main_wall")
hero_rng  = split_rng(world_rng, key = "hero_rock")
wall, anchors = cliff_wall(length = 120, rng = wall_rng)
hero0  = make_rock(size = 6.0, roughness = 1.2, rng = hero_rng)
hero   = transform(hero0, translate = (12, 0, 8))
scene  = merge(wall, hero)
output scene
output anchors
tap stats: scene
```

Обратите внимание на три вещи. Во-первых, группа `flat_tops` размечается **после** `mesh_from_sdf` — SDF не переносит атрибуты и группы (§8.4, атрибутный барьер), поэтому `@slope` считается на стене заново, а не переносится из `make_rock`. Во-вторых, все валуны стены в MVP — одна immutable SDF-форма (§8.4); повторяемость маскируют `@scale` и `@orient` на точках линии, а рядом стоящий hero-валун — уже отдельной формой из `make_rock` и склеивается со стеной обычным `merge`. В-третьих, у `cliff_wall` каждый стохастический потребитель получает собственный `split_rng` — ни один `rng` не питает два узла (линт §6.5).

## 18. Приложение C: независимость реализации и границы интеграции

PGG проектируется как новая самодостаточная система. Существующие генераторы, форматы мешей, кэши и рендер-проходы не являются нормативными, не ограничивают внутреннюю модель PGG и не обязаны переиспользоваться. Цель greenfield-реализации — устранить накопленные ограничения, а не воспроизвести их под новым синтаксисом.

- **Семантическое ядро изолировано:** AST/IR, типы, геометрия, поля, `rng`, валидатор, исполнитель и кэш не зависят от UI, рендера, формата ассетов или текущих генераторов движка.
- **Алгоритмы выбираются по контракту спецификации:** реализация шума, извлечения поверхности, proximity и булевых операций принимается по golden-тестам, инвариантам, качеству и бюджетам, а не по совпадению с существующим кодом.
- **Интеграция только через адаптеры:** внешняя сторона предоставляет входные ассеты и значения `param`, затем забирает объявленные `output` как `geo<K>`, `sdf` или скалярные данные. Адаптер не протекает в семантику языка.
- **Форматы хранения и рендера — отдельные контракты:** подключение к конкретному движку, сериализация и отображение произвольных атрибутов проектируются после стабилизации MVP runtime. Ни один существующий vertex format не считается универсальным форматом PGG.
- **Зависимости реализации заменяемы:** CPU/GPU backend, библиотека точных предикатов и формат импорта могут различаться по платформам и входят в capability/numeric profile. Отсутствие опциональной зависимости диагностируется явно, а не меняет семантику остальных узлов.
- **Размещение файлов и build-интеграция ненормативны:** они определяются отдельным implementation plan и не являются частью языка.

**v1.26 (2026-09-09)** — **константно-строковые имена атрибутов/групп сквозь binding'и в статической схеме** (§7.6; грамматика и коды ошибок не меняются): name/domain-аргументы `set`/`mark`/`unmark`/`promote`/`remove_attr`/`rename_attr`/`clip`/`bevel`/`extrude`/`inset`/`bake_ao` считаются доказуемыми литералами не только синтаксически, но и когда ident связан ровно одним flat-binding'ом с константной строкой — параметр def'а материализуется таким binding'ом (`piece[0].grp = "iron"` — литерал вызывающего), поэтому идиома `mark(placed, grp, ...)` со string-параметром больше не открывает схему. Эффект: схема выхода def'а с param-именем остаётся закрытой, `instance_on_points` получает `instanceSource` и через def-источник, `realize` отдаёт схему источника + `@tint` на points — конфликт доменов/typeinfo одноимённой колонки ловится статической E609 на загрузке (инцидент `lamp_fence`: `stone_pier` с `domain = faces` × `picket_fence` — раньше только в рантайме; обход в `blockwork.pgg` — явный `domain = points` — оставлен как merge-безопасная идиома). **v1.10 (2026-09-05)** — `sdf_grind`: притирка контактов по срединной поверхности (новый builtin §8.4, грамматика не меняется):

- **Семантика (контракт).** `sdf_grind(a, b, gap)(p) = max(a(p), a(p) − b(p) + gap)`: `a` разрезается поверхностью равной углубленности `{a == b}` в зоне взаимного проникновения с отступом `gap/2` в свою сторону (у встречных контактов `|∇(a−b)| ≈ 2`, поэтому добавка — `gap`, а не `gap/2`). Стоимость eval — как у вычитания; операция симметрична (порядок кладки не нужен, в отличие от одностороннего отпечатка `sdf_subtract(a, sdf_displace(b, −g))`, который к тому же врезает в новый камень всю глубину перекрытия).
- **Сьют `SdfGrind`** (`src/tests/pgg/sdf_test.cpp`): срединная поверхность двух шаров и щель == gap точно, `gap = 0` — общая плоскость, no-contact бит-в-бит / near-touch разводится, grind по union соседей режет каждый контакт, срединная поверхность следует значениям полей на fbm-псевдо-SDF. Сьют `SdfImprint` документирует геометрию отпечатков (взаимная резка даёт щель `перекрытие + 2·gap` — историческая мотивация притирки).

Обход тела зеркалит scope-механику валидатора: имя state изначально — входной порт; единственный binding `state = ...` становится новым определением имени (чтения до него — от входного порта, после — от binding'а) и связывается с выходным портом; петля — ребро выход→вход, помечено loop (рисуется обратной связью отдельным цветом); внешние имена читаются через рамку напрямую; вложенные зоны — рекурсия. Header питает вход первой итерации (init/collection), финальное состояние стекается в header (result).
- **Layout детерминирован (культура N1), hint побеждает** (`src/libs/pgg/src/layout.h/.cpp`): Sugiyama-lite — слои по longest-path от источников (петлёвые рёбра зон из расслоения исключены), порядок в слое — barycenter предшественников/потомков, 4 sweep-прохода с чередованием направления, ничьи — по (span.line, span.col), координаты — сетка (слой, строка) с кумулятивными ширинами колонок; зоны — рекурсивный layout тела, рамка = bbox детей + паддинг, header в title-полосе рамки. Нода с валидным hint'ом получает hint-координату вместо layout'ной (авторское намерение; локальные пересечения допустимы). Один и тот же файл → те же координаты на любом прогоне (тест-детерминизм на корпусах).
- **Формат hint'а и write-back (критерий «переживают машинные правки»).** Пин формата: `@pos X Y` (целые, любой знак; центр ноды в scope-координатах) **в любом месте trailing-комментария** строки binding'а, первое совпадение — hint; грязный/обрезанный (`@pos abc`, `@pos 1`, `@position 1 2`) молча игнорируется — никаких диагностик. `applyPosHint(text, line, x, y)`: совпадение есть → заменяются только координаты в совпавшем спане (текст комментария вокруг не трогается); нет → дописывается `  # @pos X Y` в конец строки (после существующего trailing-комментария — парс «в любом месте» это покрывает). Запиненные тестами инварианты: re-parse после write-back — `astEqual` с исходным; `format()` вывода с hint'ами их сохраняет; write-back идемпотентен при повторе с теми же координатами.
- **PggViewer (`src/apps/PggViewer`)** — read-only viewer §10, sibling PggTool'а (сознательное отклонение от суффикса Playground: постоянный инструмент, не одноразовый прототип): sokol_app + sokol_imgui, **без новых зависимостей** (ноды/провода — ImDrawList; imnodes не вводим). Canvas: боксы-ноды (заголовок = имя, подпись = op; out-пины справа, in-пины слева), провода-Безье, пан (drag пустого / RMB), зум к курсору, текст масштабируется с зумом; зоны — рамки с портами, петля отдельным цветом; def-call — двойная рамка + метка `[k]`; чипы param/output/import/tap. Проваливание: дабл-клик по def-ноде → тело инстанса (param/output чипы интерфейса), breadcrumb с instance path, Esc/кнопка — назад, вложенно; def'ы из импортов — через `loadModuleClosure`, их scope'ы помечены origin-файлом и read-only. Пробники: выбор ноды → инспекторы schema/stats/coverage/table → **синхронный** `pgg::runFile` с `RunParams::probes` (путь — имя binding'а на верхнем уровне, `<ipath>.<local>` в проваливании, instance path у def-ноды; параметры файла вводятся в панели Params); записи — текстом в панели. **v1.5 (2026-08-30)** — E7 реализован (зоны §5.4 — repeat/foreach с `@iteration`/`@piece_index`, fracture §8.11, islands §8.3, линт W004/W005 §6.5; оба критерия §15 E7):

- **Архитектура зон — runtime-конструкты движка, не развёртка.** `iterations` (repeat) и число кусков (foreach) известны только в рантайме, поэтому статического развёртывания нет: engine регистрирует zone-targets в `topLevel_`, `evalBinding` диспетчит на `evalRepeatZone`/`evalForeachZone` и мемоизирует все targets в `env_` (ленивость N2: зона исполняется только когда её target потянули — output/probe). Тело исполняется как под-программа в локальном scope (`execBody`): операторы идут в порядке текста, resolver смотрит сначала в `localEnv`, потом в outer `env_`. State/item-порты — парные порты границы: в начале итерации `localEnv[port]` = входное значение, единственный binding порта в теле перезаписывает запись (чтения до него видят входной порт, после — выходной; модель совпадает со scope-механикой валидатора). Вложенные зоны исполняются той же рекурсией. Tap внутри тела зоны в v0 игнорируется (отложено, см. ниже).
- **`@iteration`/`@piece_index` — value-семантика через стек констант** (§6.3: единственные `@`-имена-значения). `RunContext::zoneConstants` — стек пар (имя, int-значение), push/pop при входе/выходе из итерации/куска; `compileAttrRef` резолвит имя с вершины стека в константное значение (в field-контексте оно само становится Const-нодой существующей конверсией; вложенность: вершина = innermost зона). Typecheck отдаёт `int` (не field), когда имя разрешено стеком видов enclosing-зон, иначе E302 без «stage E7»; schema-closure (статический E302) эти имена пропускает — они не атрибуты. Поля тел перекомпилируются на каждой итерации (итерации материализуются, §5.4).
- **Статический typecheck зон.** Имена тел глобально уникальны (E102 запрещает shadowing), поэтому тело проверяется в том же плоском `env_`/`schemas_`/`closures_` с удалением внесённых имён при выходе. repeat: |targets| == |state| (E202); value-expr тип = типы входных портов (multi-state — multi-output call через существующий `lastSig_`/`allowMulti_`); `iterations` — value int (E205); каждый state-порт связан ровно один раз в теле (не связан → E204); дрейф типа канала → E204; targets получают типы/схемы выходных портов. foreach: collection — `geo<mesh>` (points/instances → статическая E204, v0 только mesh); item — `geo<mesh>`, связан ровно один раз; target — `geo<mesh>` со схемой выходного куска.
- **foreach: сплит, порядок, merge (общий код — `eval/fracture.h/.cpp`).** `computeIslands`: если на faces есть int-атрибут `@island_id` — компоненты = группы по id («или уже размеченные куски», §5.4), иначе union-find по общим точкам через `cornerVerts`; порядок кусков детерминирован — по возрастанию min face index, `@piece_index` = позиция в нём. `splitMeshPieces`: подмножество faces/corners + компактная переиндексация точек, attrs/groups всех доменов через `gatherColumn`, detail делится shared_ptr. `mergeMeshPieces`: N-way rigid-merge в порядке кусков с union-семантикой колонок binary merge (zero-fill, первый тип побеждает, detail — левый), без сварки. Пустая коллекция → 0 кусков → пустой меш.
- **Параллелизм foreach (N7, N1).** Перед параллельным циклом AST-обход тела собирает свободные idents (не определённые в теле/портах; enum-литералы зеркалят правило компилятора) — они force-evaluate'ятся последовательно, поэтому во время join'а outer `env_` только читается. Каждый кусок считается со **своим RunContext** (своя field-арена/кэш/диагностики/счётчики — разделяемого изменяемого состояния нет); после join диагностики сливаются в порядке piece_index, счётчики суммируются. Диспетч — новый `parallelForPieces` (parallel.h/.cpp): тот же пул, но без `kParallelThreshold` (кусок — тяжёлая единица, ≥2 уже выгодно) и с сохранением anti-nesting (per-element parallelFor внутри куска идёт inline). Результат бит-в-бит не зависит от числа потоков: rng выводится из `@piece_index`, merge в фиксированном порядке. repeat последователен по природе (цепочка состояния); параллелизм внутри итераций — существующий per-element.
- **islands (§8.3)** — union-find разметка связных компонент, пишет `@island_id` (int, faces); id присваиваются в порядке возрастания первой face компоненты (переиспользует `computeIslands`).

Модель v0 (зафиксирована в §8.11): дедупликация сайтов точным совпадением (keep-first); 0 сайтов / пустой меш / вырожденный bbox — ошибка **E608** (новый код §11); 1 сайт — входной меш с `@island_id = 0` без разреза. Куски мержатся жёстко в порядке сайтов с плотным `@island_id` (faces) = номер произведённого куска. Стохастических решений нет: ties разрешаются порядком сайтов, обязательный по сигнатуре `rng` зарезервирован под будущие модели и в v0 не читается. Два краевых уточнения, найденных тестами: `k ≤ 0` сводится к жёсткой операции (иначе 0/0); **`+inf` — нейтральный элемент smin/smax** (поле пустого instance'а; иначе `inf·0 = NaN` в редукции по якорям). `intersect_smooth` в спеке нет — не добавлен.
- **`sdf_displace` — owned копия поля + контекст сэмпла `@P`.** При создании узел глубоко копирует FieldNode-DAG в собственную арену (арена RunContext умирает после прогона, а sdf-значение живёт в MemoryCache между прогонами — тест N4 это доказывает). Контекст сэмпла: `@P` = позиция сэмпла; один валидационный проход по копии отклоняет `@N`/`@index`/`@<атрибут>`/`distance_to`/`ingroup` диагностикой **E307** (recovery: amount считается 0, ребёнок проходит без изменений — паттерн E305). Точечный evaluator `evalFieldAtPoint` зеркалит буферные формулы бит-в-бит: §6.3-функции идут через `evalExprFuncBuf` с одноэлементными буферами (та же реализация, что constant folding в `evalBuiltinCall`), fbm/vnoise/random* — прямые скалярные вызовы `fbmNoise`/`valueNoise`/`rngF32`/`rngWord` с той же раскладкой параметров (`q = at·scale`, lane = компонента). Следствие: `random*` с дефолтным `counter = index()` в displace неприменим (E307) — передавать явный `counter` (напр. `counter = 0`).
- **`sdf_instance_on_points` — трансформ как у realize + точное отсечение.** Якоря читают штамп-атрибуты `@P`/`@scale` (f32, дефолт 1)/`@orient` (vec4 (x,y,z,w) → glm::quat(w,x,y,z), нормализуется) — зеркально `realizeInstances`: `p_local = q⁻¹·(p − P)/s`, `dᵢ = source.eval(p_local)·s`; k = 0 — min-редукция по якорям в порядке `@index`, k > 0 — smin. Якоря с `scale ≤ 0` отбрасываются при создании (зеркала в SDF нет). **Точное отсечение:** якорь пропускается, если p строго снаружи его worldAABB и `dist(p, worldAABBᵢ) ≥ cur + k` — при `b−a ≥ k` smin тождественно `a`, поэтому результат бит-в-бит как без отсечения (тест с дальним якорем: EXPECT_EQ float'ов на сетке проб; sanity — ближний якорь поле меняет). Per-anchor worldAABB = трансформированный conservativeBBox источника.
- **`conservativeBBox()` — двойной инвариант (контракт узла):** (а) содержит iso-0 поверхность, (б) cull-safe: снаружи бокса поле не меньше расстояния до бокса (на этом стоит точность отсечения). sphere/box — точные; union — hull детей (+k у smooth); subtract/subtract_smooth — bbox(a) (`max(a,−b) ≥ a`); **intersect — bbox(a), а не пересечение боксов:** пересечение содержит iso, но НЕ cull-safe (контрпример найден численно: `max(a,b)` снаружи может оказаться меньше расстояния до пересечения) — отклонение от первоначального эскиза зафиксировано здесь; displace — bbox(child) ± `ampEstimate·1.3`; instance — hull якорных боксов (+k при k>0); grid — свой латтис. Пустой instance — невалидный бокс (min=+inf), `mesh_from_sdf` на нём даёт пустой меш.
- **`sdf_from_mesh` — BVH + псевдо-знак.** Детерминированный AABB-BVH над треугольниками (веер граней; mid-split по длиннейшей оси центроидов, при пустой половине — медиана по (ось, face, tri); лист ≤ 8 треугольников), ближайший треугольник по приоритету (dist, face, tri) с исследованием ничьих. Знак — псевдо-знак по нормали ближайшего треугольника `sign(dot(p − closest, n))` (для watertight-мешей корректен; открытые/самопересекающиеся меши — документированное ограничение схемы). Grid: origin = bbox меша − 3 вокселя, сэмпл — трилинейный, вне латтиса — `sample(clamp(p)) + |p − clamp(p)|`. Сэмплинг — `parallelFor` по плоскому индексу (независимые записи, бит-идентично при любом threads — тест 1 vs 8). Связку BVH позднее переиспользует `distance_to` — **в E4 distance_to НЕ рефакторился** (остался brute-force; миграция на `MeshBvh` — отдельный следующий шаг).
- **`mesh_from_sdf` — marching cubes с фиксированной таблицей.** Грид: bbox = `conservativeBBox()` + 1 воксель по периметру; страж — любая ось > 4096 вокселей → чистая ошибка **E306** (не клэмп). Сэмплинг — `parallelFor` (N7); эмиссия — последовательная в фиксированном порядке (z,y,x; рёбра в фиксированном порядке). MC — стандартная 256-таблица (public-domain, Bourke/Bloyd — атрибуция в `mc_tables.h`); позиция вершины — `t = (iso−va)/(vb−va)` со стражем `|vb−va| < eps → 0.5`; **дедуп вершин по ключу ребра грида** (unordered_map: латтисный индекс нижнего конца ребра × 4 + ось) → индексированный watertight-меш. Два факта, доказанные при реализации и запиненные тестами: **(1)** таблица Блойда face-consistent — исчерпывающая проверка всех 256 конфигураций × 6 граней (множества хорд на общей грани у каждой пары смежных конфигураций) не нашла ни одного разрыва, поэтому asymptotic decider не нужен; **(2)** при конвенции «бит i = значение < iso (внутри)» опубликованные строки таблицы ориентированы CCW **изнутри** солида (ручная проверка конфигураций 1 и 8 + тест нормалей наружу) — при эмиссии каждый треугольник разворачивается. **W002** (runtime warning): после сэмплинга, если хоть один воксель пограничной плиты ≤ iso — «sdf surface reaches the voxel grid boundary; extraction may be clipped»; статической ошибки обрезки в E4 нет (аналитический bbox консервативен; оценка амплитуды displace — эвристика). Выход — только `@P` (атрибутный барьер §8.4; `@N` — после `compute_normals`). `method` — enum {marching_cubes}, прочее → E206 (существующая машинерия).
- **Политика bbox/margin у displace:** амплитуда оценивается решёткой 4³ сэмплов поля по bbox ребёнка (`ampEstimate = max|amount|`), margin = `ampEstimate·1.3` (плюс общий 1 воксель периметра). Узкий спайк, невидимый решётке 4³, выводит поверхность за границу — это штатный путь W002 (тест с crafted-полем + прямой тест детектора на Grid-узле).
- **Кэш/фингерпринты/параллелизм:** `cacheableValue(sdf) = true` (payload самодостаточен — owned копия поля); ключ — структурный AST-фингерпринт без изменений; `fingerprintValue(sdf) = false` (uncacheable как launch-параметр — безопасное направление, с комментарием). Параллельны только сэмплинги гридов (disjoint writes); BVH-build и MC-эмиссия последовательны. Критерий N7: geoContentHash mesh_from_sdf при threads 1/8 равны (тест + корпус). Критерии N3/N4 на sdf-binding'ах: второй прогон — 100% hits по выходам; правка `voxel` у mesh_from_sdf инвалидирует только mesh-binding, а mesh, пересчитанный из кэшированного sdf-payload, бит-в-бит совпадает со свежим прогоном.

Голдены: точные counts + watertight (`nonManifoldEdgeCount == 0`) текущего profile; float — eps-допуски test_utils; N1/N7 — content-hash при 1/8 потоках равны, сводки `PggTool run --threads 1` и `--threads 8` идентичны. PggTool: sdf-output печатает `name: sdf nodes=<n> bbox=(min)..(max)` (node count по уникальным узлам DAG); OBJ-экспорт sdf пропускает с пометкой «mesh them with mesh_from_sdf».
- **Прочее:** ~12 строк «stage E2» в диагностиках/комментариях приведены к собственным этапам (def→E5, fracture→E7, топология/сэмплинг→post-E4, текущая стадия→E4, комментарий в builtins.h); тест `Typecheck.DeferredOperationsReportCleanly` перешёл с sdf_sphere (теперь поддержан) на raycast.   - **distribute_points — схема v0 с приоритетами:** per-face кандидаты `K_f = ceil(area_f · dMax_f · 4)` (константа oversample = 4; `dMax_f` — max плотности в вершинах и центроиде грани); адрес кандидата — `(rng, face_id, attempt)` (lane = attempt·5 + {треугольник, u, v, приоритет, thinning}); плотность в позиции кандидата вычисляется полем один раз на probe-геометрии всех кандидатов с барицентрически унаследованными атрибутами и группами (> 0.5); poisson `min_dist` — highest-priority-wins по spatial hash (кандидат принят ⇔ нет принятого со строго большим приоритетом в радиусе; множество единственно → результат не зависит от порядка обхода, N1 по построению); `mode = uniform` этап 3 пропускает. **Точность Пуассона (rate) не гарантируется** — контракт: детерминизм по rng, выполнение min_dist, реакция на плотность, ноль → ноль точек. Tile-компонента адреса из §8.8 в v0 не используется (стабильность face_id в пределах прогона достаточна, §5.2).
  - **merge — union-семантика колонок:** mesh (сдвиг индексов) и points, без сварки; атрибуты/группы объединяются по именам с заполнением отсутствующей стороны нулями (тип берётся у стороны-владельца, численные колонки конвертируются; detail — один элемент, побеждает левый операнд); instances-merge — чистая ошибка этапа, несовпадение K — E204.
  - **realize материализует `@tint` (дефолт `(1, 1, 1)`) в point-атрибут `tint`**; трансформ `T(@P)·R(@orient)·S(@scale)` применяется по точкам в порядке `@index`, нормали только поворачиваются, кватернион нормализуется; прочие point-атрибуты источника копируются (union по вариантам с zero-fill), сварки нет. При непустом `variants` источник выбирается по `@variant` из списка (вне диапазона — E611 в `realize`, v1.15), параметр `source` тогда не используется.
  - Именованные атрибуты в статическом typecheck имеют выведенный тип f32 (схема — данные прогона, статический вывод схемы — E5); буферы исполнения типизированы фактически, отсутствующий атрибут — runtime E302.
  - `@P`/`@N` читаются на любом домене через §4.3-интерполяцию (corners — копия точки, faces — центроид, detail — среднее по геометрии); это же даёт плотность на центроиде грани в разбросе.
  - Остальное из §8.3 (subdivide/triangulate/merge_by_distance/separate), raycast/transfer (§8.9) остаются отложенными (чистая ошибка этапа); `delete` — с v1.16, `clip` — с v1.18, `islands` — с E7; edge-домена нет.
  - E0-грамматика по-прежнему не имеет многострочных вызовов: списочный литерал многострочно не пишется (одна строка = один оператор).

**v0.6 (2026-08-28)** — решение по парсеру и архитектуре сборки AST:

- **Парсер — ANTLR4 (§13.1):** рассматривались ручной recursive descent и bison/flex. Решающие аргументы: wasm-поставка состоит из просмотрщика с запечённой геометрией и парсера не содержит (вес C++-рантайма ATN несущественен); сгенерированные файлы коммитятся как артефакты, поэтому Java-инструмент нужен только при правке грамматики. Зафиксированы обязательства: совместный пин версий jar/рантайма, CI-проверка протухших артефактов, свой error listener с маппингом в E1xx, trivia на hidden channel для форматтера.
- **Сборка AST — грамматический композитор (§13.2):** `.g4` содержит только однострочные триггеры `gc`, вся логика сборки — в `gc`. Два канала данных: семантические значения правил (`returns` + метки) для конструкций фиксированной арности и кадры накопления `gc` (`beginX`/`endX`) для открытых тел (def, зоны, файл). Listener/visitor не генерируются, `.g4` осознанно C++-specific; `gc` обязан переживать незакрытые кадры при error recovery.

**v0.4 (2026-08-28)** — типы, RNG, корни и независимость:

- **Виды геометрии отделены от доменов атрибутов:** `geo<K>` использует `K = mesh|points|curve|instances`, голый `geo` полиморфен; `sdf` остаётся отдельным типом без таблиц атрибутов.
